
This answers *what surfaces exist, and in what form does agent-generated UI arrive?* It is the decision underneath [the canvas holds the state and the chat explains it](../principles/canvas-holds-state-chat-explains.md), and the frame inside which [Conversation moves](Conversation%20moves.md), *The board and the pieces*, assigns each move's artifact to a pane.

## 1. The option field

The choice is two-dimensional: *where* agent output lives, which is the geometry of surfaces, and *how* its form is decided, which is the mechanism of agent-generated UI. The field is the industry's rather than any one framework's. CopilotKit's [generative-UI catalogue](https://www.copilotkit.ai/generative-ui) names implementation paths within it, but the geometry half is older and wider than that catalogue, and the direction's own concept — *the living document* — is a named pattern in it with shipped exemplars.

### Geometry — where agent output lives

| Pattern                                       | What it would mean here                                                                      | Verdict                                                                                                                                                                                                                        |
| --------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threaded chat, transcript as the only surface | Everything the agent produces — controls, repairs, comparisons — renders as transcript cards   | Set aside. The transcript becomes the record, which is the framing's first failure mode, and [the canvas is the durable locus of state](../assertions/canvas-is-the-durable-state.md) can't be exercised                                                                                                                   |
| Chat plus living document                        | A split workspace: chat one side, a durable object the other, both parties acting on it        | *Chosen.* It is the concept itself. What ships under this pattern grows prose and code artifacts, and a structured, solver-checked agreement as the artifact is the part nobody has shipped ([the unshipped intersection](../../research/gaps.md#unshipped-intersection)) |
| Document-first, assistant embedded            | The document is the whole surface, the assistant is invoked in place, and conversation is transient | Set aside as the primary shape, because it is *the spreadsheet that talks* ([direction](../direction.md), *Concept*), giving up elicitation. Its kept half binds here: the canvas has to work with chat idle, for the returning operator     |
| Suggestion layer on the document              | Agent proposals arrive as pending marks on the agreement, accepted or rejected in place      | Not a rival geometry, but the pattern the chosen one borrows for [revision is an ordinary move, not a restart](../principles/revision-is-an-ordinary-move.md) and [the agent proposes and the user decides](../principles/agent-proposes-user-decides.md). Repairs-as-proposals, provenance tags and one-move reversal are redlining moves, and it is named so it can be studied deliberately rather than reinvented         |
| Chatless — the agent acts through the app UI      | No chat surface, and the agent manipulates the configurator directly                             | Set aside. It removes the channel that answers the articulation barrier, and [generated in-chat controls work better than free text](../assertions/generated-controls-work-better-than-free-text.md) becomes untestable                                                                                                                             |

### Form — how agent-generated UI gets its shape

| Mechanism | What it would mean here | Verdict |
|---|---|---|
| Open-ended — the model composes markup per turn | The boilerplate's `generate_a2ui` | Set aside for anything the user can act on, under constitution #1 and #5: an LLM composing option lists can offer values the solver never vetted. The objection is to composed affordances, and doesn't reach a read-only rendering, as the note after this table explains |
| Declarative — the agent returns a schema the frontend renders | The boilerplate's A2UI path, and server-driven UI generally | Available and unused. It is held in reserve for a card whose shape isn't known in advance |
| Static — hand-written components the agent selects by tool | The payload is computed server-side from solver state | *Chosen* for every configurator card. It is the current position rather than a closed one, as the note after this table explains |

The chosen patterns compose: the living document is the geometry, static components are the form, and the suggestion layer is the grammar of the agent's proposals on the document. Each chosen pattern is also a research target, because how its mature implementations handle the mechanisms this concept needs is retrievable evidence, registered as [the living-document teardown](../../research/gaps.md#living-document-teardown).

*What the form choice is closed on, and what it is not.* The verdicts rule a mechanism in or out for the cards that exist. They don't settle the form of artifacts not yet drawn, and either of the two paths held in reserve may be admitted if it makes the resulting experience better. The constitutional objection is narrower than the row it sits in. An LLM may not compose an affordance, because a control it composes can offer a value the solver never vetted (constitution #1 and #5). That is a rule about what the user can click rather than about what the user can read. A read-only rendering offers nothing to act on, so a chart, a breakdown or any other reading whose shape follows from the configuration is outside the objection entirely, and is the case where the declarative and open-ended paths become live candidates rather than reserves. Three conditions would have to hold. Every figure in the rendering comes from a tool result rather than from the model's own arithmetic. The rendering carries no path back into the configuration. And anything the user can act on returns to the static path with a server-computed payload. Admitting a mechanism for presentation is not admitting it for control, and the two are separable here because the grammar already routes every action through one validated path.

## 2. What follows from the choice

*The document holds the centre, by default.* The geometry names two surfaces but not their weight. By default the agreement takes the primary area, and the chat sits beside it in a pane the user sizes. The user may temporarily give the chat the whole surface, or put it away entirely, and the app never does either, and never on the user's behalf ([chat-surface spec](../../specs/chat-surface/requirements.md)). Placement is the cheapest evidence for [the canvas is the durable locus of state](../assertions/canvas-is-the-durable-state.md): a surface the layout treats as secondary *by default* won't be read as the record, whatever the state actually lives in. A user choosing to look at the chat for a minute is a different thing from the layout treating the canvas as secondary, and an app that opened them in a transcript would be doing the latter.

*Valid by construction.* Each card's payload is computed from solver state at call time. `ask_choices` returns per-variable options with invalid values flagged for greying in place and the cheapest completion marked, and repair cards carry their own ripple. What the user can click is what the solver admits, which is how constitution #5 holds on a clickable surface.

*One grammar.* Every activation — a chip, a repair card, a canvas row edit — dispatches the same visible structured user message through the same validated path. The alternative, a silent programmatic run, was set aside: it is faster, but it hides user actions from the dialogue and creates a second interaction grammar ([canvas design](../../specs/agreement-document/design.md)).

*Presentation stays out of product data.* Which control renders a variable is a server-side heuristic over the model's structure — ordered groups to a scale, small domains to chips, consequence-heavy to a detail list, several at once to a form card — rather than metadata in the product model. Constitution #2 holds: adding a component needs no UI decision.

*Controls accelerate, never gate.* Free text stays available for every question a control answers. This is what keeps the pattern a conversation with controls in it rather than a form with a chat window attached, which is the failure mode [generated in-chat controls work better than free text](../assertions/generated-controls-work-better-than-free-text.md) names.

*Where each artifact lives* is settled per move in [Conversation moves](Conversation%20moves.md), under *The board and the pieces*. The artifacts moves produce — a pending question, an active repair set, a comparison — are document-side objects that appear, evolve and retire on the canvas, with chat carrying their narration. The built frontend still returns all three as chat cards, and realigning it is a pending amendment to the [canvas](../../specs/agreement-document/requirements.md) and [nonlinear interaction](../../specs/nonlinear-interaction/requirements.md).

## 3. Edges this model does not settle

- The per-artifact form on the canvas, and the status vocabulary it uses. That is canvas anatomy's question, drawn in [Canvas anatomy](Canvas%20anatomy.md).
- Which form the readings that aren't the agreement itself arrive in: a footprint or price-breakdown card whose shape varies with the configuration, or a reading of the agreement over time. This is where the declarative or open-ended paths would earn their place, under the conditions *The option field* sets (the [footprint spec](../../specs/environmental-footprint/requirements.md)).
- What the split does on a small screen. Under `lg` the two panes stack vertically, so both stay reachable, but the pattern has only ever been exercised at desktop widths and is untested against any principle. Their pixel floors apply side by side only, and a short viewport can leave either pane too small to work in.
