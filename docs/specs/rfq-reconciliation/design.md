# RFQ reconciliation — design

Rules RFQ ingestion: the paste entrance with no new surface, the solver's `seed`, the third choice source and the frozen reference, the derived deviation register, and the fixtures. Read it before changing what a document ingests or what the register holds; where the canvas draws that register is the [agreement-document design](../agreement-document/design.md).

## Entry: paste into chat, no new surface

The document arrives as a message in a fresh workspace's conversation: no upload UI, no new endpoint. Freshness is enforced, because `ingest_rfq` refuses an agreement that already has recorded choices. A dedicated paste target on workspace creation was considered and rejected, since it would add a second entry path for one gesture, and the conversation is the surface under test.

The composer's paperclip isn't a second path either, but the same one: a text file attached there reaches the agent as text inside the message ([chat attachments](../chat-attachments/requirements.md)), so paste and attach are indistinguishable by the time ingestion sees them, and nothing in the rest of this design changes with the gesture. The agent recognizes a requirements document, calls `describe_product`, and maps each clause to a `(variable, value)` pair with the clause's quote attached. Translation is the LLM's job (constitution #1), and everything after the mapping is solver work inside one tool call.

The stage-1 vocabulary line: fixture documents speak only the `agreement`, `context` and `performance` groups, the outcome layer plus building facts. A document that names `platform`, `dimensions`, `doors` or `cabin` values is prescriptive territory, and belongs to stage 2.

## Solver: `seed`

This evolves the [solver service](../solver-service/design.md), whose spec now carries the operation.

`ConfigSolver.seed(requirements)` makes every requirement a soft constraint at weight 1 on an `Optimize` over the model — the same machinery as `repairs()`, with nothing held hard. The optimum partitions requirements into `kept` and `dropped`.

*The subset objective, which was open in [problem-framing](../../discovery/problem-framing.md), *Open questions the framing does not settle*, is fewest deviations first, with the cheapest monthly completion as tie-break.* Fewest deviations is what a tender response maximizes — the compliance count — and it is the register the assertion is about. Minimizing price instead would manufacture deviations the customer never asked to discuss. Ties are real, because two equal-count subsets can exist, so equal-count optima are enumerated with the same blocking loop `repairs()` uses, bounded at about five, and the subset whose price-completion is cheapest wins, which is deterministic and explainable. Requirement *weights*, must against should, are deferred to stage 2: stage-1 fixtures have no priority vocabulary, and inventing one would be data the document doesn't state.

*There are two counts, deliberately.* The objective counts distinct requested variable-and-value pairs, and the register counts *requirements*, one per clause. They differ when several clauses cite one value: three clauses on `service_level` are one thing for the solver to weigh and three lines for the customer to read, which is how a tender is written and answered. Weighting by clause instead would let a document drag the seeding toward whatever it happens to repeat.

Per dropped requirement, the reason is `explain(kept ∪ {dropped_one})`, a minimal core naming the rules, and the *offered* value is what the candidate completion assigns to that variable. Both are existing operations, so `seed` composes rather than re-deriving.

## State: a third source, a frozen reference, a derived register

- `Source` gains `"document"`. The seeded choices are recorded through the ordinary `apply_choices` path with that source, so provenance, statuses, candidate invalidation and write-through all come for free.
- `Configuration` gains `rfq: NotRequired[RFQ]`:

  ```
  RFQ = {clauses: [{id, clause, quote, variable?, value?, note?,
                    reconciliation?: "pending"|"waived"|"revised"}],
         budget_cap?: int}
  ```

  One list of clauses, each with an identity, and which facts a clause carries
  is what kind of clause it is ([document-clauses](../document-clauses/design.md)):
  `variable` with `value` asks for something, `variable` alone leaves the
  decision to us, and neither is a clause no product variable carries. It was
  two lists until that spec, and an entry the model could not carry was
  *demoted* from the first to the second.

  Living inside `Configuration` means it writes through `_commit` and hydrates on attach with zero new plumbing, leaving the [agreement-workspace design](../agreement-workspace/design.md) path untouched. The raw document text is stored once on the workspace record, through `workspace_store.attach_rfq`, and never enters shared state, because it is reference material rather than working state.
- *The register is derived, never stored.* A pure function computes each requirement's status against the live assignment, in this order: `met` when the live value equals the requested one, else `waived` if marked, else `revised` if marked, else `deviation`. Met wins over the marks because an agreement that lands back on the document's value complies whatever route it took — the register is a diff, not a history of moves. A clause's `variable`, `value`, `clause` and `quote` are immutable after ingestion, and tools may only move the `reconciliation` mark, which is what makes the frozen-reference criterion hold. A clause that asks for nothing is in no register row: there is no requested value to compare, so it can neither be met nor deviate. The register is always the diff between the document and the live agreement, and it can't go stale, because it is recomputed from them. A second `ingest_rfq` on a workspace that has one is an error, and so is seeding one over an agreement that already has recorded choices: the document is the *starting* position, not a layer over someone else's. Re-tendering is out of scope.
- The frozen block is carried explicitly through the transitions that rebuild the configuration wholesale — `apply_choices`, `withdraw_choices`, and `adopt_frame` until [parallel-drafts](../parallel-drafts/design.md) removed it — while the others spread the old config and keep it for free. Dropping it would erase the document, not the diff. That spec also removed the one path that rewrote every choice to `source="user"`, because a fork copies provenance instead, so a seeded agreement keeps its `document` badges across the moves that used to clear them. The register is unaffected either way, deriving from the frozen block.

## Tools

- `ingest_rfq(clauses, document_text, budget_cap=None)` is one atomic call. It validates the mapped codes, and a clause naming a variable or a value the model does not declare keeps its citation and its quote and loses only what cannot be carried, reported and never silently dropped; runs `SOLVER.seed`; records the kept requirements as `source="document"` choices; stores *seed's own* whole as the candidate; stores the `rfq` block; and freezes the text on the workspace. The candidate isn't re-solved, because `complete()` isn't unique on cost-free variables — the [solver service](../solver-service/design.md) records this — so re-solving could offer a value the seeding result never named. The tool message gives the agent everything it needs to narrate: the seeded count, each deviation as requested, offered and rules, the clauses no variable carries, the clauses the document leaves to us, the budget line, and the variables the document settles nothing on. Every step builds a new value, so a failure anywhere leaves the agreement untouched.
- `reconcile_requirement(variable, move, value=None)` is one card, one call. Every clause bearing on that variable is answered together, because they are one disagreement answered once, and the tool message names the clauses it moved. The *mark* lands per clause: a clause asking for the value the agreement lands on has nothing to answer and keeps its pending mark, which only a document contradicting itself makes visible ([document-clauses](../document-clauses/design.md), decision 4).
  - `move="accept"` pins the offered value as a `source="user"` choice, because waiving is the customer's decision and pinning stops later revisions silently moving a value they explicitly accepted, and marks the requirement `waived`.
  - `move="revise"` requires `value`, runs the same `revise()` transition as `revise_choices`, and marks the requirement `revised`. So a reconciliation that collides with other choices returns the existing repair payload and cards, unchanged, and the criterion that reconciliation goes through the revision-with-repair flow falls out of reuse rather than new code.
  - `move="open"` marks it back to `pending`, and nothing else changes.

`get_configuration` gains the register summary — deviations pending, and waived but listed — so "where do we stand" answers from state.

## Frontend

- The canvas gains a third provenance badge for `document` sources, with the clause in its popover: "your document, clause 4.2 — 'quote'". Every row the agreement doesn't currently *meet* shows requested against offered, while it is an open deviation and equally once it is waived or revised, because story three asks to see the document's ask *always*, and a reconciliation mark settles a requirement without retiring it. The header counts the same three ways. Requested values are grouped by value and never flattened onto the first clause, because a document may ask two different values of one term, and joining every clause number under one label would misquote it. It is built from the existing shadcn vocabulary, with no new component family.

  This rendering was designed against the sheet, which is what existed then. The [agreement-document spec](../agreement-document/design.md) closed the seam by moving it into the document's margin for recitals and operative terms, and keeping it as a row strip in the schedules, where the sheet survives. The badge, the requested-versus-offered wording, the grouping by requested value and the three moves are unchanged; only where the mark sits changed. A schedule holding an unanswered requirement opens itself, since an annex would otherwise hide a deviation.
- The register is derived *frontend-side too*, by the same rule, from the frozen block and values already in state. It is a diff rather than a judgment, so nothing about validity is being decided outside the solver. The *rules* behind a deviation are in state, and weren't until the task 6 walkthrough of 2026-08-20: they were narrated in chat only, so the durable record carried the ask and the offer while the reason lived in a conversation the workspace treats as disposable. They come from `Configuration.unavailable`, the same solver-derived map every unavailable option reads ([agreement-document](../agreement-document/design.md)), and the mark on the term renders them under the ask. Deleting every conversation therefore loses the negotiation and not the argument.
- Reconciliation moves dispatch *visible* structured messages — "Reconcile deviation: accept the offered Rated speed, 2.5 m/s (rated_speed=mps2_5)" — rather than the hidden `Canvas edit:` grammar. Waiving a document requirement is negotiation and belongs in the record, while sheet edits are bookkeeping and don't. That extends to the option list: picking any value on a row the document *asks something of* dispatches the *revise* move rather than a canvas edit, so a third control was never needed. A row the document speaks to without asking anything edits, because there is no requirement to revise ([document-clauses](../document-clauses/design.md), decision 6). Prompt wording and message grammar stay coupled, as everywhere.
- A colliding reconciliation returns the ordinary repair payload, so `reconcile_requirement` is registered with the same `RepairOptions` renderer as `revise_choices`. The criterion that reconciliation goes through the revision-with-repair flow therefore holds at the UI layer as well as the state layer. Its other outcomes are plain text, which that renderer already falls back on.
- The document badge is a sibling of the collapsible trigger, never a child. It is itself a popover trigger, and a button inside a button is invalid HTML that fails hydration on every load, a variant of the problem the [chat-surface design](../chat-surface/design.md) records.
- There is no new chat card. The register's home is the canvas, the durable locus, and the agent narrates the top deviations after seeding. A dedicated deviation card was considered and dropped, because it would duplicate the canvas state the way the banned aggregate price delta duplicated the comparison, and constitution #10 asks for the smallest mechanism.

## System prompt additions

Recognize a pasted requirements document and ingest instead of eliciting. Map only what the document states, with every mapping carrying its clause quote, never inventing a requirement or a priority, and record a clause that explicitly leaves a decision to us as one carrying its variable and no value, never as a mapping of the agent's own assumption. Present deviations as negotiable positions rather than verdicts: "your document asks 3.0 m/s; the rules allow 1.6 m/s here because R12 — accept it, change the requirement, or leave it open". Elicit only what ingestion reports — the terms the document settles nothing on, and the clauses it leaves to us — and keep waived requirements named when summarizing. A hardware-specified document is stage 2: say plainly that the work starts from outcomes, and ask what the figure is there to achieve. A safety clause is not one of those: it is an obligation the customer has no discretion over, recorded as stated ([document-clauses](../document-clauses/design.md), decision 5). Treat "Reconcile deviation: …" messages as one `reconcile_requirement` call, and unlike a sheet edit, confirm it, because it is negotiation and belongs in the record.

## Fixtures

Two authored documents live in `agent/fixtures/rfq/`, plain text a presenter pastes. One is satisfiable and leaves several terms unstated, giving a clean seed and elicitation targeted at those. The other is over-constrained, reusing the modernization-against-3.0 m/s conflict the repair machinery is already demonstrated on, so the deviation's core is a known quantity. They are illustrative artifacts with the same epistemic status as the pricing data. Both speak only the stage-1 groups, and every `platform`, `dimensions`, `doors` and `cabin` value in the seeded candidate is solver-forced rather than document-stated. `safety` joined the stage-1 groups with [document-clauses](../document-clauses/design.md), and neither fixture states a clause in it.

`residential-new-build.txt` states nine requirements — residential, europe, new_build, 24 m travel, 1000 kg, 1.6 m/s, medium traffic, standard service level, EN 81-70 — and leaves `contract_term`, `stops` and `connectivity_package` unstated, which are the variables elicitation has to target. Verified against the solver: jointly satisfiable, and its cheapest completion sits under the budget cap the document states, so the clean case is clean on price too.

`office-tower-modernization.txt` states twelve, of which `installation=modernization` and `rated_speed=mps3_0` are the intended conflict. Verified: unsatisfiable, with a minimal core of exactly those two choices under R04, where speed sets minimum headroom, and R28, where modernization can't raise the existing headroom. R03 and R27 are an equivalent pit-depth core the solver may return instead, so a `seed` test should assert on the core *choices* and accept either rule pair. Two single-drop maximal subsets exist, so this fixture exercises the tie-break rather than merely the count: dropping `rated_speed` offers 2.5 m/s and completes cheaper than dropping `installation`, so cheapest-completion picks the one a modernization customer would recognize as an answer. That is evidence for the objective, and a caution that the tie-break does real work here.

Both documents also carry clauses no model variable covers, by design — handover dates and liquidated damages, a 2 h response time where the premium level offers 4 h, a service-credit regime, unit counts — to exercise the clause that carries nothing.

The three questions the fixtures raised, as built:

- *Several clauses, one variable*, as in A's 4.1, 4.2 and 4.3 on `service_level`. They are kept as several requirements sharing a variable, so every citation stays true to its own clause. The two counts follow, `seed` dedupes for weighting, and `reconcile_requirement` answers the whole group at once. A document naming two *different* values of one variable needs no special case in the solver: the exactly-one structure drops one of them, and the deviation cites no named rule because none is involved. It does need one in the marks, which is what clause identity bought ([document-clauses](../document-clauses/design.md)).
- *Bounds against the register's equality test.* Equality stands, with no comparator and no ordered domains. It doesn't bite: kept requirements are pinned as `document` choices, so the live value equals the requested one by construction, and the one figure that deviates on these fixtures, B's 3.0 m/s, is stated exactly rather than as a bound. A bound would misread only after a later revision pushed a variable past it, and the wording stays "requested X / offered Y" rather than "non-compliant", so a misread is a stale line rather than a false accusation. Known gap.
- *The budget cap* is reported rather than constrained: an optional `budget_cap` on the block, compared to the candidate price as arithmetic in the tool message and in `get_configuration` — "caps the charge at €1,800; this candidate is €1,951 — €151 over". There is no solver change, because a price bound in `Optimize` would change `complete()` and interact with the maximal-subset logic, for a pressure the customer negotiates rather than a rule they break. The stage-1 vocabulary line in requirements.md stands as approved.

## Testing

Solver, in `test_solver.py`: `seed` against both fixture requirement sets, covering all-satisfiable passthrough, the modernization partition, the price tie-break, deviation rule attribution — asserting the core *choices* and accepting either the pit-depth or headroom rule pair — determinism across repeated calls, duplicate collapsing, the two-values-of-one-variable case, and unknown-code rejection.

State, in `test_configuration.py`: register derivation and its status order, the three reconcile moves, group movement across clauses, a clause the model cannot carry keeping everything it can, ingest-twice and ingest-over-a-configured-agreement rejection, atomicity, and the frozen reference surviving reconcile, apply, complete, save, adopt and withdraw. [document-clauses](../document-clauses/design.md) added the three kinds, clause identity, per-clause marks and the read-time lift to that file.

Store, in `test_workspace_store.py`: the document text frozen on the record and untouched by configuration writes.

The design's empirical claims about the fixtures were re-verified against the live solver before the tests were written, and all hold: A is satisfiable at €901/month under its €1,200 cap; B is unsat with the core `installation=modernization` and `rated_speed=mps3_0`; two single-drop maximal subsets exist; and dropping the speed offers 2.5 m/s at €1,951 against €2,021 for dropping the modernization.

## Verified in the app

Both fixtures were pasted into fresh workspaces (constitution #9).

- *B, over-constrained.* It seeded 11 of 12 requirements at €1,951/month with `document` badges throughout, a header reading "1 of 11 requirements from your document not met", the rated-speed row showing "Clause 3.1 asked 3.0 m/s · offered 2.5 m/s" with its two moves, and the agent narrating the deviation with R03 and R27 and the €151 cap breach. Accept produced the visible reconcile message, one tool call, "all 11 answered · 1 waived", and the row pinned to "you" with "waived, still listed". Reloading into a *new* conversation re-rendered the whole register from the store. Insisting on 3.0 m/s afterwards returned repair cards with the pit and headroom ripple, and left the agreement untouched.
- *A, satisfiable with terms left unstated.* It seeded 13 requirements with no deviations and no ceremony, at €1,141/month within the stated €1,200 cap, then elicited only what the document settled nothing on.
- *A synthetic third case*, seeded through the store because neither fixture produces it: two unmet clauses asking different values of one variable, alongside a revised requirement. Each clause rendered with its own requested value, and the revised one kept its ask visible with the header counting it.

Known gaps, all three extraction quality rather than machinery:

- The agent mapped A's clause 5.2, which explicitly leaves the term to us, to a 10-year `contract_term`, putting its own assumption on the sheet as something the customer asked for. The prompt named that shape — "open to proposal", "state your assumption" — and asked for an omission, which left the agent nowhere to put the clause. It now asks for a recording instead: the variable it bears on, and no value ([document-clauses](../document-clauses/design.md)). Re-verify when the conversation checks cover this.
- *Extraction isn't reliable on one clause of the office-tower fixture, and the miss is silent.* Clause 1.2 states the works are a modernization within the existing shaft, `installation=modernization` is what carries it, and the agent occasionally omits it while mapping the other eleven requirements correctly — once in seven observed runs against `gpt-5.4-mini` on 2026-08-19. Nothing about the omission announces itself: without it, the 3.0 m/s of clause 3.1 is satisfiable as a new build, the seed reports every requirement met, and the deviation the document actually contains never appears. This is the extraction half of the flow rather than the reconciliation half, so the register and the seed partition are working correctly on a requirement set that is wrong. It isn't fixed here: the candidate remedy is a prompt edit, and `compare_refs.py` is the instrument that would show whether it helped.
- The agent read B's 5.1 as `service_level` alone and left `connectivity_package` to be forced rather than citing the clause. Under-mapping is the safe direction, since nothing is invented, but the citation is thinner than the document supports.

The [tender as entrance](../../discovery/scenarios/tender-as-entrance.md) scenario is built and running ([conversation checks](../conversation-checks/design.md)). It ingests the office-tower fixture as the customer's first turn, asserts the register against a direct re-seed of the requirements the agent recorded, and drives an accept and a revise through the `Reconcile deviation: ` grammar.
