# Parallel drafts — design

Draft, tracking [requirements.md](requirements.md). Nothing here is built.

## Vocabulary

`Configuration.candidate` keeps its meaning: the solver's completion of the current choices, written by `propose_completion`, read by `resolveValue()` as the last fallback. The new entity is a *draft* — one whole configuration among several in a workspace. So a workspace holds drafts, and each draft has a candidate. The two senses of "candidate" that the discovery layer runs together ([problem-framing](../../discovery/problem-framing.md) §5 against constitution #7) are separated here in favour of the code's existing meaning, and *draft* is chosen to sit in the contract genre the canvas already renders — recitals, operative terms, schedules ([agreement-document](../agreement-document/design.md)).

## Store shape

`agent/src/workspace_store.py` record becomes:

```
{id, name, drafts: [{id, name, forkedFrom, configuration, history}], currentDraftId, threads, updatedAt}
```

`configuration` and `history` move off the record and onto each draft; `threads` and `name` stay at the workspace, because conversations are views onto the installation and not onto a draft. Draft ids are minted like workspace ids. Unlike the workspace's name, a draft's is never `null`: the tools address drafts by name, so a nameless draft would be one the agent cannot switch to, compare or discard. `fork_draft` therefore requires its name and the read-time adapter supplies "Original" for the draft it adapts. This is where the workspace naming precedent stops applying — a workspace is addressed by its id from a route, and can afford to wait for a name.

`forkedFrom` holds the id of the draft this one was copied from, and is `null` on the draft a workspace opens with. Source traceability back to the origin is the first thing every shipped branching implementation does — Manus prints a breadcrumb, ChatGPT an origin label ([branching-in-ai-uis](../../research/branching-in-ai-uis.md) §2) — and a document that says nothing about where it came from would be the one object in this system that doesn't, in a prototype where every individual value quotes its source ([choice-provenance](../choice-provenance/requirements.md)). It costs a field and a phrase beside the draft's name in the switcher. The requirements do not demand that the phrase be shown; recording the parent is what makes showing it a later decision rather than a migration. Discard leaves children pointing at an id that resolves to nothing, and the field is read for display only, so an unresolvable parent renders as no lineage at all rather than being repaired on the way out — rewriting a grandchild's parentage on discard would assert a lineage that never existed.

*A record with no `drafts` key is adapted on read:* its `configuration` becomes a single draft named "Original", carrying its `history` and no parent, and its `frames` are dropped. This is a read-time adapter rather than a migration script — `agent/data/workspaces/` is gitignored local data, and the [agreement-workspace](../agreement-workspace/requirements.md) precedent for pre-feature records is to let them lapse rather than convert them. Frames cannot be converted honestly anyway: synthesizing the missing provenance would re-source every value to `user`, which is the defect this feature removes.

## The write path, and the trap in it

`save_configuration` currently pushes onto `past` whenever `configuration != record["configuration"]`. Under drafts it compares against the *current draft's* configuration and pushes onto that draft's history. The trap is that a switch also changes what the workspace's current configuration is, so routing a switch through the same function would burn an undo slot and let a subsequent undo walk backwards into a state belonging to a different document.

The separation is structural rather than a flag: `fork_draft`, `switch_draft` and `discard_draft` are their own store functions that rearrange drafts and move `currentDraftId` without ever calling `save_configuration`. Content changes reach history through exactly one door, as they do now; structural moves do not reach it at all. `HISTORY_DEPTH` stays 10, now per draft.

Last write wins and no locking are unchanged. `_stamp` still stamps the workspace and the writing conversation.

## Agent state and tools

`AgentState.configuration` keeps its meaning and its shape: it is the current draft's configuration. Every existing tool, the canvas, `resolveValue()` and the register are therefore untouched by this feature — they read the current draft without knowing that is what they are doing, which is what keeps the change small (constitution #3, #10).

Two mirrors ride alongside, written by the same `_commit` helper that already returns undo depths, and read only for chrome: `current_draft_id` and a `drafts` list of `{id, name, price}`. The precedent is `workspace_name` and the undo depth mirror — state the canvas renders controls from, never a second source of truth. Both are declared on `AgentState`, because the AG-UI adapter filters each state snapshot to the graph's output schema and drops undeclared keys on the way to the browser with no error at either end ([copilotkit-surface](../../research/copilotkit-surface.md) §4).

A draft's `price` is nullable, and routinely null. Price lives on `Configuration.candidate`, and `_keep_candidate` drops the candidate whenever a choice diverges from it — so any draft edited since its last `propose_completion` has no price to report. The switcher shows such a draft by name alone. Solving the other drafts to fill the gap is rejected: the solver is called by tools acting on the current draft (constitution #1), and pricing every draft to draw a menu would put solver calls behind a render.

Tools, replacing the three frame tools:

- `fork_draft(name)` — copy the current draft's whole configuration into a new draft, make it current. The `name` argument is the agent's, supplied from the conversation; the docstring carries when to call it, the system prompt carries the two silences (never ask for a name, never announce the naming), per [where guidance lives](../agent-tools/design.md). It returns a `Command` updating the mirrors and nothing else: the forked configuration is byte-identical to the one it came from, so there is no content change to record, and the store's structural path never reaches history in the first place.
- `switch_draft(name)` — move `currentDraftId`. No configuration is written, nothing is re-sourced. This is what replaces `adopt_frame`, and the wholesale re-attribution to `user` disappears with it.
- `discard_draft(name)` — remove a non-current draft; refuses on the last one.
- `compare_drafts(a, b?)` — `b` defaults to the current draft. The payload is today's `frame_comparison` with `kind` renamed to `draft_comparison` and each side named by its draft. Because both sides are now full configurations rather than assignment-plus-price, the "—" fallback for a side lacking stored footprint applies only to pre-feature data.

The four-step cheapest-versus-greenest sequence taught by `propose_completion`'s docstring ([environmental-footprint](../environmental-footprint/design.md)) rewrites onto the new names and otherwise stands.

Two things outside the tools shape what the agent knows. `get_configuration` ends with a "Saved frames: …" line built from `_frames(config)`; it becomes the draft list, naming the current one, so the agent's read of state says which document it is looking at. And the system prompt gains a drafts framing beside the one [agreement-workspace](../agreement-workspace/design.md) added about other conversations: the agreement may exist as several drafts, changes land on the current one, and forking is what to offer when the customer wants to try something without giving up what they have.

## Frontend

The canvas head gains the current draft's name and a switcher listing the others with their prices — the frames strip's information, relocated from a compare-trigger under the price header to a navigation control at the document's identity. Fork, switch and discard dispatch visible structured messages in the established grammar, mapped onto one atomic tool call each, like undo's controls and unlike the hidden `Canvas edit:` path: switching changes what the whole document says, so the chat has to carry it. Because conversations are views onto the workspace and not onto a draft, one transcript will hold turns that acted on two documents, and the visible sentence is the marker that keeps that readable — a transcript that changes what it refers to with nothing recording the change is the branching genre's first named failure mode ([branching-in-ai-uis](../../research/branching-in-ai-uis.md) §2).

Two rules from [chat-surface](../chat-surface/design.md) govern the switcher and are the likeliest source of a silent breakage:

- It is a menu, so it mints React ids, so it may not join the hydrated tree. It mounts a tick later, exactly as the chat header's mode and conversation menus do. Sharing markup with the existing conversation menu must be done as a class string, not as a component lifted above id-minting descendants.
- It reads agent state, so it subscribes from a leaf that draws only itself. Nothing on the workspace page may call `useAgent()`.

The hydration seed in `use-workspace-attachment.ts` carries the mirrors too. It writes `workspace_id`, `configuration` and the undo depths into state on attach, and it is the only path for the two new fields: a thread that has never run replays no snapshot, and one that ran before this feature replays a snapshot of an `AgentState` with no `drafts` key in it ([copilotkit-surface](../../research/copilotkit-surface.md) §4). Seeding the current draft's configuration without `current_draft_id` and `drafts` would leave the document unnamed and the switcher empty until the customer's first message.

The hook's workspace-configuration precedence moves with the store shape. Its `want` is `stableStringify(record.configuration)` today; under drafts the comparison target is the current draft's configuration, selected out of the record `fetchWorkspace` returns. That is a small change in a hook whose traps are documented in [agreement-workspace](../agreement-workspace/design.md), and it is the second thing to get right there after the seed.

*The same `want` decides whether a reopened conversation's cards may still act, and there it needs the draft id as well as the configuration.* A fork produces a draft byte-identical to the one it came from, so content equality stops being evidence of draft identity for exactly as long as the fork goes unedited — the window in which a customer is most likely to reopen the conversation the fork came out of. A card left live in one conversation, with the fork taken in another, would pass the staleness check on reopening and apply to the fork. So the comparison is over the pair `(current_draft_id, configuration)`, which costs nothing: `current_draft_id` is declared on `AgentState`, so the thread checkpoint carries it. Unpinned conversations are what make this reachable at all — the branching genre keeps a branch's transcript to itself ([branching-in-ai-uis](../../research/branching-in-ai-uis.md) §4) — and of everything that trade gives up, this is the part that produces a wrong action rather than a confusing display.

The reason such a card gives is the drafts' names. [agreement-workspace](../agreement-workspace/design.md) has the inert card state why it cannot act instead of only dimming, and under drafts the sentence can be specific — *this conversation was working on Original; the current draft is Premium* — which tells the operator what to do about it, where "the agreement has moved on" only tells them something happened. Both names are to hand where the sentence is formatted — the hook, not the card: the current one from the record, the conversation's own by resolving the `current_draft_id` in its checkpoint against the record's drafts. That is the same pair the staleness check compares, and it reaches the card as the reason string [agreement-workspace](../agreement-workspace/design.md) puts on `StaleThreadContext`. Saying it well matters more here than it did there: the shipped feature needed a second conversation to have written to the workspace before anything went inert at all, where forking and switching are cheap moves an operator makes on purpose and often.

Two edges. *The conversation's draft may be gone* — C1 worked on a draft since discarded — and then there is no name to resolve, so the sentence falls back to the workspace-level wording, which is still true. *And the sentence says "was working on" in the singular*, which holds only because a card that predates a switch made inside its own conversation is already inert by the any-user-message rule and never reaches this path. Only tail cards do, and a tail card's draft is the checkpoint's draft. That is true of the inert rule as it stands and would quietly stop being true if the rule were loosened.

`FrameComparison` becomes `DraftComparison` with the renamed payload check; its two-column layout, both deltas and per-side adopt button are unchanged, and the button now dispatches a switch rather than an adopt.

## Alternatives considered

- *Pin each conversation to a draft.* This is the shipped pattern in the one genre that has tried it — VS Code and Cursor checkpoints restore conversation and files together ([living-document-undo](../../research/living-document-undo.md)). Rejected because it contradicts [agreement-workspace](../agreement-workspace/requirements.md)'s ruling that conversations are ephemeral views onto the installation, and because it would restructure the entry-resolution logic in `use-workspace-attachment`, the most trap-dense hook in the codebase, for a benefit this feature does not need.
- *Keep history at the workspace and let it cover structural moves.* Attractive for uniformity — every move reverses, says the [move inventory](../../discovery/models/Conversation%20moves.md) — but an undo taken after a switch would restore a state belonging to another document while the user looks at this one.
- *Keep frames beside drafts.* Two mechanisms for one idea (constitution #10).
- *Carry a switch as an AG-UI state delta rather than a snapshot.* The transport needs nothing added for this feature, for three independent reasons ([copilotkit-surface](../../research/copilotkit-surface.md) §4). The LangGraph adapter emits whole snapshots and no deltas at all, so the delta path would have to be built rather than used. A switch replaces the configuration wholesale, which is what a snapshot already is — the patch would restate the document. And a delta that fails to apply is caught and logged as a warning, leaving the canvas showing the previous draft with nothing marking it stale, against [always show a valid whole](../../discovery/principles/always-show-a-valid-whole.md). Size is not part of the argument: a stored configuration measures 3–8 KB, and the whole set of drafts would still make an unremarkable snapshot. The reason to keep all but the current draft out of agent state is the mirror precedent above, not bytes.
- *Fork from a point in history rather than from the current state.* Every shipped branching implementation forks at a visible message — hover the turn, branch from there ([branching-in-ai-uis](../../research/branching-in-ai-uis.md) §1). The analogue here is forking at history entry *k*, and it is rejected for want of a surface rather than for difficulty: the canvas renders no history, [undo](../undo/requirements.md) excludes a visible history timeline, and the transcript is not the state ([the canvas is the durable locus](../../discovery/assertions/canvas-is-the-durable-state.md)), so there is no point in history for the customer to put a finger on. Fork-from-current is what a document-side branch can offer, and undo remains the way back to an earlier state of one document.
- *Cap the number of drafts instead of allowing discard.* The cap would be an arbitrary number, and discard is the structural inverse of fork, which is the more honest mechanism. Proliferation is still the risk to watch: creation is cheap, every draft is visible in the switcher, and if drafts accumulate unread the affordance is wrong rather than the count.

## Testing

Store: unit tests for the read-time adapter, fork/switch/discard, the last-draft refusal, per-draft history isolation, and the criterion that a switch pushes no history entry. Agent: pure-function tests for the four tools and for `configuration` continuing to resolve to the current draft. Scenario harness: the renamed tool calls move existing assertions, and `compare_refs.py` is the only check that sees the docstring and prompt edits at all ([demo-scenarios](../demo-scenarios/design.md)). UI: browser pass per constitution #9 — fork, edit one draft, switch, confirm provenance survives and undo stays within a draft, compare, discard, cold reload with the draft's name and the switcher present before any message is sent, both themes, no hydration error on the switcher (reload twice before believing one under `next dev`). One case in that pass is not obvious, and it has to be run across two conversations or it passes for the wrong reason. Leave a live card in conversation C1 — repair options will do — then open C2 of the same workspace and fork there. Without editing either draft, reopen C1: its card must be inert, and must say which draft C1 was working on and which is current. Forking *inside* C1 would prove nothing, because the fork's own visible message makes every card above it inert by the rule `useCardDispatch` already applies.

## Open, deliberately

Where a comparison is placed, and how a two-objective comparison is laid out, stay [phase-plan](../../discovery/phase-plan.md) task 3's. This feature gives that task two real documents to lay out instead of a document and a snapshot, and the [pending amendment](../nonlinear-interaction/design.md) that would move comparisons document-side is unaffected either way.
