# Product model — design

## Decisions

- *A single JSON file*, `agent/src/product_model/elevator.json`, with no code in the model. Under constitution #2, adding a variant means editing data only.
- *Enum-only domains.* All variables, dimensions included, are finite enums — shaft tiers run `t1_1800x1700` through `t6_3000x3000`. Real formulas, such as load determining car area, are encoded as allowed-pair tables rather than arithmetic. That keeps the solver encoding trivial and the model inspectable, and numeric variables can be introduced later without changing the schema's shape.
- *Two constraint types only:* `table`, for allowed value pairs across two variables, and `implication`, where `if_all` conditions imply `then` membership. Everything observed in real configurators — requires, excludes, compatibility, code rules — reduced cleanly to these two.
- *Named rules.* Every constraint has an `id`, R01 through R54, and a `label` written as the sentence the agent should be able to say when the rule appears in an unsat core (constitution #6).
- *Two price kinds, never both on one option*, enforced by the loader, per the [service-agreement spec](../service-agreement/design.md). Hardware options carry `price`, a cost basis in EUR amortized into the monthly fee and never customer-facing, and agreement options carry `monthly_price` in EUR per month. Civil-works variables — shaft, pit, headroom — are unpriced. A top-level `pricing` block holds `financing_factor`, `term_months`, which covers the `contract_term` domain exactly, and `default_term`.
- *Agreement variables are ordinary variables* in a leading `agreement` group — `service_level`, `contract_term`, `usage_profile`, `connectivity_package` — coupled to hardware by R31–R34 like any other constraints.
- *Footprint data*, per the [environmental-footprint spec](../environmental-footprint/design.md). Every option carries `co2`, the embodied kg CO₂e before the multiplier, with negatives allowed, required by the loader whenever the model has a `footprint` block, including on price-free variables like `travel` and `stops`. `energy_package` and `energy_class` are ordinary enum variables in the platform group, coupled by R35–R40. A top-level `footprint` block holds the named assessment assumptions and the `annual_kwh` table, keyed by energy class, usage profile and travel band, covering those domains exactly.
- *Negotiable equipment beyond the shaft.* Five variables cover what a real sale argues about once the geometry is settled: `dispatch_control` in the platform group, `rescue_operation` and `firefighters_operation` in a `safety` group, `access_control` in the cabin group, and `lead_time` in the agreement group. Each was admitted on one test: does it create a move the model couldn't previously make? Dispatch reaches from hardware into the recurring fee, because R41 forces the connected package. Rescue is forced by the drive the platform already fixed (R43). Firefighters' operation is the model's second region-split rule after accessibility (R46) and carries the longest cascade in the model, from situation to lift to doors to backup (R47–R49). Floor access is the only equipment a building type forces for reasons of use rather than code (R51). And lead time trades the handover date against made-to-order finishes (R52–R53), a pair with no technical coupling at all. Serves discovery principle [elicitation uses the building's vocabulary, not the catalogue's](../../discovery/principles/elicit-in-the-buildings-vocabulary.md): each is reachable from something the specifier can say about the building — how the lobby behaves at nine, what happens in a power cut, who may reach the guest floors, when the building opens.
- *One exception to the price-kind split:* `lead_time` sits in the `agreement` group but carries `price` rather than `monthly_price`, because the handover date is a term of the agreement whose cost is a one-off slot bought from the factory queue. The loader enforces the split per option rather than per group, so nothing else changes.
- Grounding: EN 81-20 dimension tables and KONE MonoSpace planning data supply the numbers, the platform-caps-performance structure comes from Tacton-style CPQ, and the initial scale target of about 23 variables and 30 rules, since grown, was chosen per the Sisyphus-VT benchmark discussion in [the configuration field review](../../research/configuration-field.md).

## Known gap: D-rules

Constitution #6, as amended, specifies a second rule series the model doesn't yet carry: D-ids, named default heuristics beside the R-ids, grounding the agent's discretionary choices the way cores ground its refusals ([Conversation moves](../../discovery/models/Conversation%20moves.md), *Delegation moves*). The model holds R01–R40 only, and agent-chosen defaults carry free-composed reasons, which is a standing violation of #6 rather than merely an omission. It closes when the delegation machinery gets specced. Until then, treat any D-rule reference in the discovery models as target state.

## Validator

`agent/src/product_model/validate.py` builds a Z3 model, one Int per variable over option indices, and checks several things.

It checks global satisfiability, dead options through a per-value SAT probe, the scenario suite from the requirements, the agreement-coupling scenarios from the [service-agreement spec](../service-agreement/design.md) — R31 forcing, R32 and R34 conflicts — and a pricing check, that for identical choices a longer term yields a lower monthly fee.

The [environmental-footprint spec](../environmental-footprint/design.md) adds energy-class determinacy, where every feasible drive-and-package pair forces exactly one class; the R35 conflict scenario; the energy-table shape checks for standby inversion, conditional regeneration and class monotonicity; and embodied calibration against the 8.5 t EPD anchor.

The equipment rules R41–R53 are checked as forcings rather than conflicts: the tall-European-office cascade from lift to fire-rated doors to battery backup, the region split, the machine-room-less rescue rule, the two destination-control preconditions, and the hotel access rule, plus the expedited-handover conflict.

The reference configuration used for the embodied anchor is checked for completeness against the variable set, so a variable added without a reference value fails loudly instead of quietly leaving the anchor unchanged.

Run it from `agent/` with `uv run python src/product_model/validate.py`. It has to pass after any model edit.
