# One gesture, one action — design

Rules which action a dispatched sentence reaches: every `Set …` message, from an in-chat control or from the agreement sheet, is one `revise_choices` call. Read it before changing the prompt's rule for a card sentence, either content tool's docstring, or the ontology's gesture table.

Status: implemented and verified 2026-08-21, offline and against the live agent. The routing is enforced in the tool rather than asked for in the prompt — see *The prompt asks, the tool enforces*, which is a mechanism the requirements don't mention and the live run made necessary.

## What the prompt says

A dispatched message reaches a tool only through the model, so the first place the rule lives is a paragraph of the system prompt. What changed is that the paragraph no longer asks a question. It is not the only place — the section after this one is why. The *Messages that are not conversation* bullet for `Set <term> to <value> (term=value)` names `revise_choices` with `source="user"`, says the routing holds whether or not the terms were decided, and forbids `set_choices` outright. The canvas-edit bullet points back at it instead of saying "record the edit", which read as `set_choices` to anyone — model included — who knows which tool records.

The sentence itself is unchanged, which the requirements make the default and design has to justify departing from. Keeping it costs nothing and buys four things: `CARD_PREFIXES` in `spokenText` still strips codes from the customer's own bubble, the Python mirror in `agent/tests/scenario_grammar.py` still matches character for character, `PROMPT_FRAGMENTS` and `ONTOLOGY_SENTENCES` in the coupling check still pass, and a transcript holding sentences in the built wording still resumes correctly. The mint sites could tell a decided term from an undecided one — the canvas holds the configuration, the ask card's payload carries a status per option — and neither needs to, because the answer no longer changes what happens.

Two tool docstrings carry the other half, because a docstring is what the model reads at the moment of the call. `revise_choices` argued for itself only where something had been decided earlier, which is an argument against the case this change adds; it now says it covers anything set through a control or the sheet, decided or not. `set_choices` says what it is for — choices the agent read out of prose or proposed itself — and sends a dispatched value to `revise_choices`.

## The prompt asks, the tool enforces

Prose alone did not hold the routing. On the opening turn of a fresh conversation the model reached for `set_choices` on four consecutive runs, through three successive strengthenings — leading with the rule, forbidding `set_choices` by name, saying it holds on an empty agreement, and taking `set_choices` out of the `describe_product` docstring and the catalog listing that primed it. A single-variable dispatch did it too, so batch size was not what drove it. Against an empty agreement nothing can collide, the two actions are indistinguishable in outcome, and "revise" reads wrong for a first entry, so the model resists exactly where the rule appears to cost nothing.

It does not cost nothing. A form card computes each variable's valid options independently, so two picks in one card can separate, and that batch would half-land under `set_choices` where this feature says it must refuse whole.

So `set_choices` refuses a dispatched sentence. `_is_gesture` reads the last human message off the run state, `is_gesture` decides whether it is one, and the tool returns a refusal naming `revise_choices` and recording nothing. The agent retries in the same turn. The last human message is the whole of what a gesture is: a structured sentence a card or the sheet dispatched, with nothing else in the run to distinguish it from prose.

*The `Set` form is matched on its shape, not its first word.* "Set up an elevator for a hospital, 12 floors, busy mornings" is an ordinary opening message, and refusing it would send a batch the agent translated out of prose to a total action — losing the partial application that protects the values outside a collision, in the very walkthrough that motivated it. The parenthesised code is what no customer types, so the match requires `Set … to … (var=value)` and requires it of every line: one such line beside a sentence of the customer's own is prose. `"Canvas edit: "` needs no such care, because nobody types it.

*The refusal covers the turn, not the values.* A gesture turn cannot reach `set_choices` at all, including for something the agent wanted to record beside the customer's change. Nothing in the built flow does that, and the narrower rule would need the tool to compare its arguments against the sentence, which is the parsing the grammar exists to avoid.

Two costs, both accepted deliberately. The card grammar now exists in four places — `src/lib/configurator.ts` mints it *and reads it*, `agent/main.py` teaches it, `configuration.py` refuses it — so the coupling check runs the real predicate over the agent's own sentences and asserts the set in both directions: exactly `choiceMessage`, `canvasEditMessage` and the prefix are guarded, no reconciliation or draft move is, and four prose messages are let through. The fourth copy is `isGesture()`, which the transcript uses to draw no row for a gesture ([agreement-document](../agreement-document/design.md)); the same check holds it against the agent's predicate over the same sentences and over the same prose, because a rule that grew there would take a customer's typed message off their own screen. And `set_choices` gains a dependency on the transcript, which is what a narrower rule would have to read anyway.

*Known gap: that case refuses whole and offers nothing.* When the changes contradict each other rather than the agreement, no repair to the other choices can help, so `SOLVER.repairs` raises and the agent gets the conflict with its rules instead of a repair payload. Half of the requirements' promise holds there — it applies whole or not at all — and the repair-paths half does not. `set_choices` would at least have recorded the picks outside the collision, so this is the one place the feature trades a partial landing for a refusal with nowhere to go. Closing it means repairs computed over a contradictory request, which is a solver question and its own change.

The prompt keeps its rule. The guard is a backstop, not a substitute: an agent told nothing and corrected afterwards would spend a tool call on every gesture.

## What stays partial, and why the bullet stayed

`set_choices` keeps its semantics and its rationale untouched, so [the agent-tools criterion](../agent-tools/requirements.md) that a batch with a collision inside it records everything that can hold stays true of the path it describes. The [agent-tools design](../agent-tools/design.md) records why partiality was built: an opening turn naming an office in Frankfurt, twelve floors, 25 m of travel and a 1000 kg car had the whole batch refused by R14 and the completion refilled the emptied variables as a residential building.

The reversal this change makes is worth stating as one. The same five values arriving from a multi-variable control now refuse whole. That is deliberate — the customer picked each of them in a control that showed which were valid, so half of them landing silently is worse than repair paths they can click — and it is the one place where the feature makes something less forgiving than it was.

The Method bullet on revising rather than recording afresh stays, against the handoff that planned to retire it with the ambiguity. It rules the *prose* path, which the requirements put out of scope, and the [agent-tools design](../agent-tools/design.md) records a measured A/B saying the prompt is the only place it works from: the scenario was a typed revision, "actually I need 3.0 m/s", and moving the rule to the docstring alone took `revise_choices` from 5/5 to 2/3, losing the repair cards in the runs it lost. Deleting the bullet would have regressed the case it was measured on. It is reworded to say it is about what the customer *tells* you, and to point at the dispatched-message rule for everything else, so it can no longer be read as licensing `set_choices` for a gesture on an undecided term.

## Checks

Three offline assertions carry the routing, in `tests/couplings.test.ts`, and each was mutation-tested:

- `ONTOLOGY_ACTIONS`, beside `ONTOLOGY_SENTENCES`, names one action per element of the grammar. Each is asserted to be a tool the agent builds, and to be the action the gesture row carrying that sentence names — with no ` or ` in the cell, which is the shape finding 1 had.
- The prompt's rule for the `Set …` sentence names `revise_choices`, and mentions `set_choices` only to forbid it. `onlyForbids` draws that line, so reverting the bullet to "One set_choices call" fails while the prohibition passes.
- The tool layer's copy of the grammar is compared by running it: the dump reports which of the agent's own sentences `is_gesture` matches, and which of four prose messages it lets through. Both sets are asserted whole, so a rule that grew or shrank fails.
- The canvas-edit rule names the same action.

Four tool tests in `agent/tests/test_tools.py` cover the guard itself: a dispatched `Set …` message and a `Canvas edit:` one are both refused with nothing recorded, and two prose messages record as before — an ordinary sentence, and one opening on the word *Set*, which is where matching the first word would have broken the path this feature leaves alone. Three more cover the paths the routing sends work down: a conflicting pick on an undecided term comes back as repairs, a half-conflicting batch records nothing including its innocent half, and a clean batch of undecided terms applies whole with `source="user"`. Mutating `revise_choices` to refuse flatly, to record partially, or to attribute the change to the agent fails them.

The scenario harness gains two assertions and no turns: the dispatched setup batches in mid-contract revision and in `_priced_office` are asserted to reach `revise_choices`. They set terms nobody had decided, so before this change they were `set_choices` turns, and they are the cheapest live evidence that the model obeys the unconditional rule.

## Verification

Offline, 2026-08-21: `uv run pytest`, `npm test` and `npm run typecheck` all green. Every assertion added was mutation-tested and each mutation was caught, on both sides of the boundary where both see it. The ones worth naming, because they are the regressions this feature exists to prevent: removing the guard, making it fire on every message, matching the sentence on its first word, dropping the parenthesised code from what it requires, and putting `set_choices` back in the prompt's rule.

Live, 2026-08-21, `pytest -m scenario` plus one throwaway probe. What the routing does divided cleanly by whether the change could collide, and the guard closed the half that prose could not.

*Where a collision is possible, the prompt already held.* Four dispatched changes against an agreement with content reached `revise_choices` and came back with repairs before the guard existed: a sheet edit on a decided term (mid-contract revision, turn 4), a chat pick and a sheet edit on an *undecided* term colliding with a decided one, and the dispatched setup batches of the comparing and renewal scenarios. The middle two are the [conversation-checks](../conversation-checks/design.md) third known gap closing, observed rather than argued.

*Where it did not, the guard does.* Mid-contract revision's dispatched setup now reaches `revise_choices`, and the suite passes all five scenarios.

*The prose path kept what the [agent-tools](../agent-tools/design.md) A/B measured.* The typed revision still framed as a revision and still produced cards, so rewriting the `revise_choices` docstring and narrowing the Method bullet cost it nothing.

*One scenario is flaky, and not over this.* Needs, not nomenclature failed `cascade_forces_a_bed_car` and `cascade_forces_wide_doors` on the first run, `agent_picked_the_cabin` on the second, and passed on the third. It is the one scenario barred from the structured grammar, steering in prose throughout, so no dispatched sentence occurs in it and the guard never fires. Renewal as revision failed once on a different thing and passed afterwards: the agent invented the value code `s1800x1700` for "1800 by 1700" instead of `t1_1800x1700`, which fails the same way under either action, and its reply quoted the real code at the customer, which the voice rules forbid. Both are recorded as observed rather than diagnosed; separating a model change from an inherited one is what `compare_refs.py` is for, and it has since been run — see below.

*Confirmed against the previous tree, 2026-08-22.* `compare_refs.py HEAD` over all five scenarios reports the repair where the guard was supposed to show it, and nowhere else. Three dispatched setups that reached `set_choices` on the earlier tree — the comparing, renewal and mid-contract batches — reach `revise_choices` on this one, and each is a structured message, which is the near-deterministic class. That is the finding this feature exists to produce, and it is now measured across two trees rather than argued from one.

*What flaps, and what does not.* Three runs of this tree — the standalone suite, the full comparison's arm, and a single-scenario comparison — fail a different assertion each time and share none. The earlier tree flaps too, on the cabin choice and on the shaft turn, where it invented `w1800_d1700` while this tree recorded the real code: the same defect the run above saw as `s1800x1700`, inherited rather than introduced. Two assertions move for a structural reason instead, `it_keeps_its_own_log` and `the_accepted_requirement_is_waived_not_dropped`, both reading a log the earlier tree does not keep. No assertion fails on both runs of either tree, and the three dispatched-setup movements above are the only ones that repeat.

*One intermittency is not accounted for by the prose class, and is left open.* `revising_is_one_reconcile_call` failed once in three runs of this tree, with no `reconcile_requirement` call on the turn at all, and passed on every run of the earlier one. Its turn is dispatched through `revise_requirement_message`, so it belongs to the state-critical class the [conversation-checks design](../conversation-checks/design.md) calls near-deterministic, and the prose explanation that covers the others does not reach it. Three runs are too few to separate a rarer nondeterminism from a real weakening, and this session rewrote both `reconcile_requirement`'s docstring and the message it returns, which is the surface a dispatched reconciliation reads. Recorded as observed. What would settle it is repeated single-scenario comparisons over that one turn.

*The app, 2026-08-21.* A fresh elevator seeded from prose, then both gestures, with the thread's tool calls read back from the running agent. The prose turn recorded through `set_choices`, so the guard reaches the dispatched sentences and stops where prose begins. `Canvas edit: Set Rated speed to 2.5 m/s (rated_speed=mps2_5)` reached `revise_choices`, left no bubble in the chat, took the *you* badge on the sheet, and the agent spoke only about the pit depth, headroom, battery backup and firefighters' lift the rules then forced. An in-chat chip, `Set Service level to 24/7 call-out…`, reached `revise_choices` on a term the customer had not decided, showed visibly with its tool chip, and repriced.

*What the app run showed that no check does.* A colliding gesture is not reachable from a single-value editor. The option editor renders ruled-out values struck through and unselectable — 3.0 m/s was already struck against the recorded modernization — so the customer cannot dispatch a change that collides with what the sheet says. The paths that reach a collision are a multi-variable card whose own picks separate, a card left open while the agreement moved under it, and a change made in another conversation. That narrows where this feature's repair path fires, and it is the same set the guard exists for.

*That narrowing is closed, 2026-08-30.* It was a property of the controls rather than of this feature: a struck-through option was `disabled`, so the gesture could be seen and not made. Under constitution #17 nothing is disabled to mean no, and all four controls that draw a ruled-out option — the card's chips, scale and list, and the sheet's `OptionEditor` — dispatch it like any other. The sentence, the routing and the prompt are unchanged, which is the point: `Set <term> to <value> (term=value)` already reached `revise_choices` "whether or not the terms were decided", and it now also reaches it whether or not the value is currently valid. So the repair path fires wherever a customer asks for something the rules currently forbid, which is the case it was built for and the one it could not previously be shown. What still holds is the known gap above: a request contradictory *on its own* refuses with nowhere to go, and a single struck option asked for on its own is never that — it collides with the agreement, which is exactly what `SOLVER.repairs` takes.

*One defect observed, and not this feature's.* The chat composer throws "Maximum update depth exceeded" from `src/components/ui/textarea.tsx` through `InputGroupTextarea` and `ComposerTextArea`. Nothing here touches React beyond two comments. It is recorded because it was seen, and belongs to whoever takes up the [chat pane](../chat-pane/design.md).

## Reconciled with this change

The routing was stated in six places besides the prompt, and they moved together (constitution #15):

- [ontology](../ontology-of-phenomena/ontology.md): the first two gesture rows name `revise_choices` alone; the draft row names its four tools instead of "the four draft moves", so every row a grammar element lands on names actions rather than describing them; the `set_choices` and `revise_choices` notes say what reaches each; settlement 3 no longer defers atomicity of effect to finding 1; and finding 1 is retired in place, keeping its number because the findings after it are cited by theirs. The [ontology design](../ontology-of-phenomena/design.md)'s decision 5 and its audit note said this would be the first repair spec, and now say it was.
- [conversation-checks](../conversation-checks/design.md): the third known gap closes for gestures and stays open for prose; the A/B paragraph says the regression it caught was a typed revision; the renewal paragraph keeps its 630 kg car for a reason that survives — the turn it protects is prose.
- [agreement-document](../agreement-document/design.md) and its requirements: the canvas-edit round trip and the `ask_choices` form both named `set_choices` as the action, in two approved criteria and two design paragraphs.
- [nonlinear-interaction](../nonlinear-interaction/design.md): a repair was said to be recorded "through one `set_choices` or `clear_choices` batch", which the built tool already contradicted; it is one `revise_choices` call carrying both drops and changes.
- [agent-tools](../agent-tools/design.md): the quoted Method bullet, a paragraph saying the rule now covers prose only, and a note on the partial-rejection design saying a dispatched batch does not get it.

Checked and left alone: [rfq-reconciliation](../rfq-reconciliation/design.md), which routes through `revise()` and is unaffected; [undo](../undo/design.md), whose two mentions of `set_choices` are about the agent re-recording a value and about never rebuilding one from the transcript; and the dated browser-pass records in [shared-attention](../shared-attention/design.md), which say what happened on a day and are history rather than rules.
