# Agreement document canvas

The canvas is the agreement in its own genre: a layered service-agreement document — recitals, operative terms, schedules — rendered as a projection of solver state and editable in place. This spec owns that surface whole: what it shows, how it is layered, and the edit grammar every value on it uses. The in-chat option controls belong here too, because a control the agent raises with `ask_choices` dispatches the same structured message a value on the document does; the grammar is one, wherever it is activated. Drawn and argued in the [canvas anatomy model](../../discovery/models/Canvas%20anatomy.md); the parameter sheet is the schedule layer, not a second view.

Serves discovery principles [elicitation uses the building's vocabulary, not the catalogue's](../../discovery/principles/elicit-in-the-buildings-vocabulary.md) — the record answers in the language elicitation speaks, instead of re-imposing catalogue terms at the primary surface — and [the canvas holds the state and the chat explains it](../../discovery/principles/canvas-holds-state-chat-explains.md). This surface plus the chat is the hybrid the research argues for ([interaction-literature](../../research/interaction-literature.md), thread D). Puts three assertions under test: [the representation of the agreement selects the user's moves](../../discovery/assertions/representation-selects-moves.md), [the canvas, rather than the transcript, is the durable locus of state](../../discovery/assertions/canvas-is-the-durable-state.md), and [generated in-chat controls work better than free text](../../discovery/assertions/generated-controls-work-better-than-free-text.md).

## Stories

- As a building operator, the canvas reads as my agreement, not a parts list: what will happen at my building in plain language, the commitments with their price and footprint, and the machine spec as an annex — something I could defend to an owner as it stands.
- As a building operator, I orient on the document rather than on the transcript: what has been decided and by whom, what the rules forced, what is still open, and what it costs per month, all visible beside the chat (constitution #7).
- As a non-expert, technical values carry short situational glosses ("1000 kg — thirteen persons; a stretcher fits"), so I can make sense of the hardware annex without leaving the page or asking.
- As a reviser, every value remains editable in place, wherever it renders — the document genre costs me no revision access, I never have to ask the agent to make a change, and options ruled out by my other choices are physically unselectable (constitution #5).
- As a delivery lead, the full parameter schedule is still there, complete and tabular, one expansion away.
- As a customer the agent asks something in chat, I get an input control fitted to the question — chips for a quick either/or, a scale for load or speed, a detail list for cars and finishes, a compact form when several things are asked at once — instead of having to type part nomenclature (constitution #4; the articulation barrier). Typing a free-text answer always remains possible; controls are accelerators, not gates.
- As the agent, I see document edits the same way I see chat commitments, so I can react to them — announce newly forced values, warn about consequences, update the candidate.

## Acceptance criteria

Layout:

- GIVEN a workspace with configuration state, WHEN the canvas renders, THEN the agreement appears as three layers in order: *recitals* (the site, the situation from the `context` group, and what will happen — installation, operation, term — as prose in building language), *operative terms* (the `agreement` and `performance` groups as numbered clauses, closing on the consideration: monthly price and modelled lifetime footprint), and *schedules* (the remaining hardware groups as the existing sheet, collapsible and collapsed by default). Every variable in the model appears in exactly one layer.
- GIVEN a candidate in state, WHEN the canvas renders, THEN the monthly price is readable without scrolling as well as stated as a term, and the objective it was completed against is named rather than presented as neutral; GIVEN no candidate, THEN the document says none has been proposed yet.
- GIVEN any value shown in recitals or terms, WHEN it changes in agent state, THEN the rendered prose updates — the document is a projection with no drift, and recitals prose is produced by deterministic templates over state and model data, never composed by the model (constitution #6 extended to the record).
- GIVEN provenance and status data, WHEN the document renders, THEN who-chose-what and pending states use document-native marks — attribution and the deviation register in the margin beside the clause they qualify, on the sheet's rows in the schedules — preserving the same distinctions the sheet shows today: user-chosen, agent-chosen, rule-forced, open ([the agent proposes and the user decides](../../discovery/principles/agent-proposes-user-decides.md)); open values show the candidate's proposal visually distinct. A variable is marked once, in the layer its group belongs to, even where another layer restates its value.
- GIVEN an empty configuration, WHEN the canvas renders, THEN the document renders as a skeleton — the same three layers with their values blank — with the existing invitation to describe the project in chat.

Editing. "Value" below means any configurable value, wherever it renders — a row in a schedule, a term, or a token inside a recital sentence:

- GIVEN any configurable value in any layer, WHEN the user activates it, THEN it opens the same option editor and dispatches through the same solver-validated path: the hidden `Canvas edit:` structured message, or the visible `Reconcile deviation:` one where the customer's own document speaks to that variable (the [rfq-reconciliation spec](../rfq-reconciliation/requirements.md)'s move). Which of the two is a property of the variable, not of the layer the click landed in.
- GIVEN a value's editor is open, WHEN statuses mark options invalid, THEN those options are visibly disabled and unselectable; selectable options show labels and monthly price deltas.
- GIVEN the user selects a valid option, WHEN the edit is dispatched, THEN it is recorded through the same `set_choices` path as chat input (source "user"), and the document subsequently reflects refreshed statuses — including any newly forced cascade — without further user action.
- GIVEN the user selects a valid option, WHEN the click lands, THEN the value shows immediately (optimistically), and WHEN the round trip completes, THEN it renders from validated agent state — identical for a clean apply, corrected for a rejection or revision.
- GIVEN an edit that applies cleanly, WHEN the round trip completes, THEN nothing appears in the conversation — no echo of the choice and no agent commentary; the document is the only surface that changes. GIVEN an edit that forces other values, conflicts, or needs repair, THEN the agent's explanation of that consequence (and only that) appears in chat.
- GIVEN the agent is mid-run, WHEN the canvas renders, THEN editing is disabled and the running state is indicated.
- GIVEN a consequence-heavy technical value, WHEN it renders in any layer, THEN its situational gloss is derived from model display data, not composed at render time. Which values carry one is the model's own answer: an option annotated with a gloss is glossed wherever it appears, in a term as much as in a schedule.

In-chat controls — the agent asks via one tool (`ask_choices`), and the control type is selected per variable:

- Control vocabulary: *chips* for short unordered domains (roughly ≤6 options: building type, door type, installation); *scale* (segmented, ordered) for ordered domains (load, speed, travel, stops, door width, dimensions), where invalid segments render greyed in place so the user sees the valid range narrow; *detail list* for long or consequence-heavy domains (car sizes with dimensions, finishes with prices) showing label, description, and price delta per row.
- GIVEN the agent asks about several related variables at once (e.g. "tell me about the building"), WHEN the message renders, THEN a single form card composes the per-variable controls with one submit, and submitting records all filled fields as one `set_choices` batch (unfilled fields stay open).
- GIVEN any control, WHEN it renders, THEN it offers only options valid at call time (computed server-side from solver statuses), greys out invalid values in place rather than hiding them, shows price deltas, and marks the cheapest-completion value.
- GIVEN the user activates a control (chip tap, scale selection, list pick, form submit), WHEN the choice is submitted, THEN it lands in state via the validated path and the agent acknowledges it in its next message.
- GIVEN the user ignores a control and instead types an answer (or asks something else), WHEN the conversation continues, THEN earlier controls become inert history — no stale submission is possible.

## Relationship to RFQ reconciliation

The agreement document is the outbound half of a real-world genre pair whose inbound half is the [rfq-reconciliation spec](../rfq-reconciliation/requirements.md)'s document: request and response, joined by the deviation register — a compliance matrix. The layering here explains that spec's stage boundary: a stage-1 RFQ speaks exactly the recitals and operative-terms layers and lacks the schedules; a prescriptive RFQ is one that enters the schedule layer. Both specs record the seam between them. Because rfq-reconciliation landed first, this spec reconciles how the register is rendered: in recitals and operative terms a deviation is a margin mark on the affected clause ("your document asked X, clause N"), carrying the same moves it carried as row decoration; in the schedules it stays a row strip, because a schedule row *is* the sheet. Its moves and its wording are unchanged in both. The RFQ itself is never rendered as a surface. Both specs also share one discipline from opposite directions: text is never the state — inbound text is interpreted into solver-checked commitments, outbound prose is projected from them.

## Out of scope

Typed free-text editing of the document — the follow-on named in the [canvas anatomy model](../../discovery/models/Canvas%20anatomy.md) §4, to be specified separately. Export/print/PDF generation (the [service-agreement spec](../service-agreement/requirements.md)'s exclusion of contract document generation stands — this spec is the live canvas, not an output artifact). Relocating in-chat repair sets and pending revisions onto the document (the amendment tracked by the [surface architecture model](../../discovery/models/Surface%20architecture.md) §2 — this spec builds the target surface but does not perform the move). Multiple named candidates, comparison view and revision-ripple visualization, all the [nonlinear-interaction spec](../nonlinear-interaction/requirements.md)'s, including where a comparison is placed. Deleting the legacy todo/a2ui example components. Mobile layout.
