# Agreement workspace — design

Rules the durable workspace: the store on the agent side, write-through, the HTTP surface, and the attachment hook's hydration and precedence. Read it before touching `src/hooks/use-workspace-attachment.ts` or anything that seeds configuration on entry, and before changing how an elevator is named, renamed or deleted.

## Store (agent side)

`agent/src/workspace_store.py` writes one JSON file per workspace under `agent/data/workspaces/`, which is gitignored: `{id, name, configuration, threads: [{id, createdAt, updatedAt}], updatedAt}`. `configuration` became `drafts` plus a `currentDraftId` under [parallel-drafts](../parallel-drafts/design.md), which owns that shape and its read-time adapter. `name` is `null` until the agent names the workspace through `rename_workspace(id, name)`, and creation takes no name.

The store lives on the Python side because tools are the single validated mutation path (constitution #1, #3) and have to write through to it; a frontend store would duplicate state (constitution #3). File-per-workspace JSON is the smallest mechanism that survives restarts (constitution #10), so there is no database.

Creating a workspace seeds `empty_configuration()`, with solver-derived statuses, so the canvas of a fresh workspace is complete before any conversation.

## Terminology and naming

The user-facing term for a workspace is *elevator* — list heading, back link, empty states — while code, store and routes keep *workspace*.

Naming works like conversation auto-titles. The workspace starts unnamed, and the frontend shows the placeholder "New elevator", styled as such. The agent calls the `name_workspace` tool once the conversation identifies the installation, or with a short descriptive name when enough context exists without an explicit identity, and renames when better identity emerges. It never asks the customer for a name and never announces the naming. Under [where guidance lives](../agent-tools/design.md), when to call it is the tool's docstring, and the two silences are voice rules in the system prompt.

The tool persists through `rename_workspace` and returns a `Command` updating the new `AgentState.workspace_name` field, so the open workspace's canvas header re-renders with the name immediately; the list page reads it from the store on the next load. Display precedence is resolved once in `use-workspace-attachment.ts` and handed to the canvas as a prop: `agent.state.workspace_name` ?? fetched `record.name` ?? placeholder. `get_configuration` reports the current name from the store, so the agent knows whether the workspace is already named well enough.

The operator can overwrite it, through the control described in *Renaming*. That does not relax either silence: the agent still names unprompted and still never asks. What changes is that the name it chose is no longer the only one available — a name the agent inferred from a passing mention is a guess, and the operator is the one who knows the building. Both doors write the same `named(Workspace, Name)` fact through the same store call, and neither is authoritative: last write wins, and because `get_configuration` reports the stored name, a rename by either is what the other reads next.

## Agent state and write-through

- `AgentState` gains `workspace_id: str`, absent on legacy threads, so it is read with `.get`. The frontend seeds it into agent state when attaching a conversation, and it persists in the thread checkpoint thereafter.
- Every mutating tool — `set_choices`, `revise_choices`, `clear_choices`, `propose_completion`, `reconcile_requirement`, `ingest_rfq` — calls one helper after computing the new configuration. The helper persists to the store, to the current draft, when `workspace_id` is present, then returns the usual `Command`. The structural draft moves deliberately don't go through it ([parallel-drafts](../parallel-drafts/design.md)). Read-only tools are untouched. Last write wins, and there is no locking.
- That helper also stamps `updatedAt` on the *conversation* doing the writing, read from the run's own config — the `configurable.thread_id` of `langgraph.config.get_config()` — rather than from agent state, which doesn't carry it. This is what "where the operator left off" resolves to on entry, as *Frontend* describes. A thread the workspace hasn't registered yet is skipped rather than created: registration stays message-triggered on the frontend, and it stamps the conversation when it happens.
- The thread checkpoint still carries `configuration`, as the historical record of what that conversation saw, which is exactly what cross-conversation staleness detection compares against.

## HTTP surface

Custom routes are mounted into the LangGraph dev server through the `http.app` key of `langgraph.json`, pointing at a small FastAPI app in `agent/src/http_app.py`: `GET /workspaces`, `POST /workspaces` (no body needed, since workspaces are created unnamed), `GET /workspaces/{id}` (the whole record, drafts included), `PATCH /workspaces/{id}` (rename it, see *Renaming*), `DELETE /workspaces/{id}` (destroy it, see *Deletion*), and `POST /workspaces/{id}/threads` (register a conversation). The frontend reaches them through a Next.js rewrite from `/api/workspaces/*` to `localhost:8123/workspaces/*`, which is same-origin and needs no CORS. The mounting works under `langgraph dev` — langgraph-api 0.7.x logs "Loaded custom app" — so the fallback of a separate process wasn't needed.

## Deletion

`delete_workspace(id)` unlinks the record and returns nothing. The record is the container — drafts, their logs and entries, the clauses and the frozen document text are all inside the file — so one `unlink` ends the whole population and no sweep follows. There is no archived state, no trash and no undelete, which is the scope decision in the requirements; undo could not have served as one either, since the log a reversal walks is inside what is destroyed. It goes through `_path` like every other call, so the id guard covers the one destructive path as well, which matters more here because the id arrives from a URL segment.

The route answers `{"deleted": id}` rather than 204. `request` in `src/lib/workspaces.ts` reads every response as JSON, and a body keeps the one helper covering every route. A missing record is a `KeyError` and a 404, mirroring `GET`, so deleting twice — two tabs on one list — refuses rather than reporting a second success.

*It is reached by no tool.* Creation is already an action of the frontend rather than of the agent, and deletion follows it: a conversation that could destroy the agreement it is about would put the whole record within reach of a misread sentence, and nothing in the journey asks for it. This is why the ontology files it under *reached by no tool* and why it writes no log entry — there is no log left to write into.

`DeleteElevator` in `src/components/workspace/` is the whole frontend: a trash button whose label names the elevator and what goes with it, and a call to the store on the click. It takes the follow-up as a prop, because the two placements need different ones — the list re-reads itself, the open agreement navigates out to the list. A failed delete leaves the control where it is and says so, rather than reporting a deletion that did not happen.

*There is no confirmation step,* asked for explicitly. A dialog was built first and taken out; what stands in its place is that the control states what it destroys before it is clicked, and nothing else on either surface deletes anything. The cost is stated rather than mitigated: a mis-click destroys the agreement, its drafts and their logs, and the store has no undelete to fall back on. Removing the dialog also removed the last Radix primitive here, so the component mints no React ids and joins the hydrated tree as it is — the [chat-surface](../chat-surface/design.md) gate the draft switcher needs does not apply to a plain button.

Two placements, both asked for: a row of the elevator list, and the breadcrumb at the head of the canvas, where the elevator's identity and the way back already are. The list row stopped being one anchor to take it. `Item asChild` wrapped the whole row in a `Link`, and a `<button>` inside an `<a>` is neither valid markup nor clickable, so the link now covers the row through an `after:absolute after:inset-0` overlay on the name and the controls sit in a `relative` `ItemActions` above it. Row hover and keyboard focus keep their border, the second through `has-[a:focus-visible]`.

An elevator deleted while another conversation has it open is out of scope, under the same concurrency decision that lets the last write win. The page that is looking at it fetches on entry and on thread change, so it keeps rendering agent state until something sends it back to the store, and then reports that the elevator does not exist — the `notFound` branch that already existed for a bad id.

## Renaming

`rename_workspace(id, name)` in the store predates this and is unchanged: it trims, refuses a name with nothing in it, stamps `updatedAt` and writes. What was added is a second door onto it, `PATCH /workspaces/{id}` with a `{name}` body, answering with the whole record. The agent's `name_workspace` tool reaches the same call, so the two cannot leave a name the other reads differently, and the route answers with the record rather than an acknowledgement so the control renders the name the store *kept* — the store trims, and a control showing what was typed would disagree with the list on the next load. An empty name is a 400 rather than a quiet 200: the control has a sentence to say about why the elevator kept its name, and cannot say it if the route reports a rename that did not happen. A missing record is a 404, mirroring `GET` and `DELETE`.

*The name is edited where it is written,* in both places it appears: a row of the elevator list, and the breadcrumb at the head of the open agreement — the same two placements deletion has, and for the same reason, since the head of the canvas is where the elevator's identity already is. `RenameElevator` in `src/components/workspace/` serves both. It owns the name's *display* as well as its editing, because those are one spot on the page: the caller passes what the name looks like when nobody is editing — a link in the list row, a span in the breadcrumb — as children, and the control swaps that for a field in place. The follow-up is a prop, as `DeleteElevator`'s is: the list re-reads itself, the open agreement keeps its own display in step through the attachment hook.

*Edit in place rather than a dialog,* and that is not only a preference. Both placements sit in the hydrated tree, where a Radix `Dialog` or `Popover` would mint React ids and shift every `useId` on the page ([chat-surface](../chat-surface/design.md)). An input, a form and two buttons mint none, so this joins the tree as it is — the same property that removing the delete confirmation bought `DeleteElevator`.

*The field opens on the name, not on the placeholder.* An unnamed elevator opens an empty field: "New elevator" is what the list says about an elevator with no name, not a name anybody chose, and offering it as the text to edit would make it look like one.

*Confirming an empty name is answered, not refused* (constitution #17). The confirm button stays live and takes the click, and `sayWhy` says that an elevator needs a name to be renamed to and that this one keeps the one it has. A rename already in flight is guarded in the handler, with a spinner, on the pattern the create and delete controls already use — a ref beside the state, because the state is read from a render's closure. A rename that fails leaves the field open holding what was typed and renders a sentence beneath it that the input points at with `aria-describedby`, rather than a `title` only a mouse can raise (constitution #16). Cancelling is Escape or the cancel button, not blur — a blur handler would have to tell the confirm button's own focus loss from leaving the field, and the sentence the refusal says names Escape rather than promising a behaviour the control does not have.

*The mirror has to be corrected, not just the record.* This is the one non-obvious part. Display precedence is `agent.state.workspace_name` ?? fetched `record.name` ?? placeholder, and the tool writes that mirror so a naming shows up mid-conversation without a refetch. So in a conversation where the agent has named the elevator, an operator's rename that wrote only the store would persist and *not appear* — and worse, `get_configuration` would report the new name to the agent while the canvas still showed the old one. The window is narrower than it first looks, and the browser pass is what measured it: the seed in the attach effect *replaces* agent state with the five keys it writes, `workspace_name` not among them, so a page load or a conversation switch drops the mirror and precedence falls to the record. A thread whose checkpoint carries `workspace_name` was opened and it showed the store's name, not the checkpoint's. What is left is the live case: the agent names the elevator mid-conversation, its `Command` puts the name in state, the subscriber has already disarmed because the user acted, and nothing re-seeds until the next load. That case is the one this callback is for. `useWorkspaceAttachment` therefore returns a `renamed(name)` callback, which updates its own copy of the record and writes `workspace_name` when agent state already carries it. It is corrected there rather than in the control because that hook is where precedence is resolved, and a second place resolving it is how the two would drift. The mirror is touched only when the key is already present: a conversation the agent has not named anything in has no mirror to correct, and adding one would put a name into the next run's initial state that nothing asked for.

The alternative was to flip precedence so the fetched record always wins and refetch after a rename. It was rejected: the mirror exists precisely so the agent's own naming lands without a refetch, and flipping it would trade a fresh defect for the one it was built to prevent.

## Frontend

- `/` is the elevator list page: name or placeholder, price of the current candidate if any, conversation count, last activity, and a one-click "New elevator" create that navigates straight in. No chat mounts here.
- `/workspaces/[id]` holds two surfaces scoped to one workspace, the agreement canvas and the chat, described in *The split*. `CopilotThreadsDrawer` is replaced by `src/components/workspace/conversation-menu.tsx`, a conversation list built from the workspace record, with rows labelled by date and grouped by day. The drawer lists all threads globally, which is the wrong entity. The menu is drawn in the chat's own header rather than in a column of its own, because the list is a view onto the pane it changes and belongs with it ([chat-surface](../chat-surface/design.md) decision 7); the workspace's name and the back link to the elevator list sit at the head of the canvas instead. The provider stays *uncontrolled*, and its original rationale holds: the menu drives threads imperatively through the configuration's `setActiveThreadId` and `startNewThread`, which the uncontrolled provider permits, and those calls stay on the workspace page.
- Opening a workspace lands on the conversation the operator left off in — the one whose `updatedAt` is latest, meaning the one that last *changed* the agreement. `latestThread` in `src/lib/workspaces.ts` computes it, falling back to `createdAt` for conversations registered before the store stamped activity. Its transcript hydrates, and only a workspace with no conversations yet mounts a fresh, unregistered one, the provider's minted thread. Returning to an installation resumes the negotiation where it stopped, and a new conversation stays something the operator asks for.

  Last-changed rather than last-started is what makes the landing coincide with the staleness rule instead of fighting it. The conversation that last moved the agreement is by construction the one whose checkpoint still matches the workspace, so a single operator working alone never lands on a stale transcript. Last-started would drop them onto a newer conversation they had already abandoned to make a change elsewhere — behind the agreement, and flagged for it. What remains is the honest case: another conversation moved the agreement while this one was away, which is precisely what staleness exists to announce. A conversation used only to ask questions doesn't update, and doesn't need to, because it changed nothing and so isn't stale either.

  Conversations registered before the store began stamping activity compare on two different clocks — one conversation's "last changed the agreement" against another's "was registered" — so in a workspace that predates this, a conversation that changed nothing can win the comparison against one that did. That is a property of the existing data rather than of the rule, the next write from either conversation settles it, and nothing migrates old records.

  The conversation *menu* keeps ordering by start time, so the landing conversation isn't always its first row. Its rows are labelled by when each conversation started, and sorting those labels by a different clock would read as broken; the active row carries a check instead. Either way the canvas renders from the seeded workspace state whether or not anyone chats. A conversation joins the workspace's list on its *first message*, whether that message was typed, suggestion-clicked, or started by a canvas edit's structured message. Registration is message-triggered rather than button-triggered, and additionally gated on the attach having completed for that thread, because a stale render right after a thread change still shows the previous thread's messages. So "a canvas edit starts a conversation" needs no special path.

## The split

In `src/components/workspace/workspace-split.tsx`, the agreement canvas holds the primary area and the chat sits to its right in a panel the operator drags to size. Position carries precedence: the centre column is what the user is working on, and the assertion [the canvas, rather than the transcript, is the durable locus of state](../../discovery/assertions/canvas-is-the-durable-state.md) isn't credible while the chat holds the left half and the agreement is the thing pushed aside. The panel group holds the whole viewport, and there is no third column, because the same argument applies to a permanent register of transcripts: the conversation list travels with the chat's header ([chat-surface](../chat-surface/design.md) decision 7) and the workspace's identity travels with the canvas.

It is built on shadcn `resizable`, which wraps `react-resizable-panels`, added to the [component library](../ui-component-library/design.md). The default is canvas 62% and chat 38%, with pixel floors of 360px each rather than percentage ones. What makes a pane unusable is its width, and a percentage floor that reads fine at 1600px is cramped at 1100px. The chat floor is measured: at 320px the comparison table overflows its card and CopilotKit's composer breaks onto a second row. Together the floors are 720px, under the group's width at `lg`, the narrowest viewport that still shows the panes side by side.

This replaced or gave up two things:

- *The Chat/App mode toggle is gone*, and with it `src/components/example-layout/` and its `enableAppMode` and `enableChatMode` frontend tools. Those were starter code from the todo demo, and nothing in the system prompt referenced them. App mode collapsed the canvas to zero width, which contradicts the placement decision, and the drag handle does the rest of its job. Under `lg` the panes stack vertically instead of hiding the chat, so both surfaces stay reachable without a toggle.
- *`useDefaultLayout` is not how the split is persisted.* It restores the last drag from localStorage, which the server can't see, so the SSR pass would render default sizes and hydration stored ones — a hydration error on every load. The split *is* remembered, through a cookie the server reads before it renders ([remembered split](../remembered-split/design.md)), and 62/38 is the division an operator who has never dragged the handle gets. The panel group and handle carry explicit `id`s against the same hazard: without them `useId` supplied the ids and diverged the same way.

*This split is sidebar mode*, one of four geometries the user can put the chat in ([chat-surface](../chat-surface/design.md)). None of the preceding changes: sidebar is the default, the only mode a load can land in, and still the drag-to-size split with its measured floors. The other three take the chat panel's contents out of the flow with classes and empty its box with a flex override, so this group's layout state is never written to and a dragged split survives a trip through them — and, for the same reason, none of them can change the remembered one. The `useId` hazard also governs what may be added to this page, which is why chat-surface's mode menu has to mount *after* hydration.

## Hydration and precedence

`use-thread-resumption` became `use-workspace-attachment`, in `src/hooks/`. On opening a workspace or switching conversations it fetches the workspace record; messages hydrate from the thread endpoints as before, and `configuration` seeds from the *workspace*, never the thread checkpoint. The draft assumed run-initial-state semantics would be enough, and verification proved four more mechanisms necessary.

- *The connect overwrites the seed.* The connect fired by a page load or thread switch delivers the thread checkpoint's state, or nothing for a fresh thread, *after* the seed. Precedence is therefore enforced event-driven: an agent subscriber, `agent.subscribe({onStateChanged})`, re-asserts the workspace configuration whenever agent state stops matching it, and disarms the moment a user message exists that wasn't hydrated from the server. From then on state belongs to the live run.
- *The agent instance swaps identity.* The agent from `useAgent` is replaced when the initial connect lands, and a seed or subscriber applied to the stale instance is invisible to the UI. The attach effect re-runs on agent-instance change — it must not be guarded to run once per thread — and re-attaches idempotently.
- *The active thread survives navigation between workspaces.* The active thread and the agent's messages are global to the CopilotKit core rather than scoped to the provider, so client-side navigation from one workspace to another carried the previous workspace's conversation along: its transcript rendered in the new workspace, and its lingering message count registered a ghost conversation there. Entry therefore *resolves* the thread rather than assuming one. An effect keyed on `workspaceId` fetches the record and either activates its latest conversation or mints a fresh one, and nothing else in the hook runs until it has. Both the attach effect and the registration effect are gated on entry having resolved *for this workspaceId*, and entry clears the `clearedFor` and `attachedFor` refs synchronously as it starts, because those refs are workspace-agnostic and would otherwise let the previous workspace's thread pass the attach gate in the render before the new thread lands. Messages are still cleared synchronously alongside the state clear on every thread change, since no connect wipes them in the navigation case. The fetch runs twice on entry, once to choose the thread and once inside the attach, which keeps `workspace` state owned solely by the attach effect and so never observable against the wrong thread. The cost is one extra local request.
- *A stale conversation can be landed on, not only reopened.* Because entry resumes a conversation rather than minting a blank one, an operator whose agreement was moved by a *different* conversation can land directly on a transcript flagged stale, with its cards inert. Choosing the last-changed conversation, as *Frontend* describes, keeps this to the case the flag is actually about — someone else's conversation moved the agreement — rather than making it routine. It doesn't make the landing read-only either: `StaleThreadContext` is consumed only by `useCardDispatch`, so the canvas dispatches its edits regardless, and the returning operator can still edit as well as read.

Three further traps are inherited from the thread-resumption era, discovered in the [nonlinear-interaction](../nonlinear-interaction/design.md) verification and handled here ever since.

- *Tool-call shape conversion.* The history endpoints return LangChain-style tool calls, `{id, name, args}`, which have to be converted to the AG-UI shape, `{id, type, function: {name, arguments}}`, or `setMessages` throws.
- *The connect can wipe hydrated messages.* A thread switch fires a `connect` that can wipe the store, so hydration waits for the agent to settle and briefly re-applies if wiped.
- *Stale state seeds the next run.* Switching clears the agent's *messages* but leaves the previous thread's `configuration` on `agent.state`, and AG-UI's `prepareRunAgentInput` sends `agent.state` as every run's initial state, so a lingering configuration would seed the next conversation and persist into its checkpoint. The hook therefore clears state on each thread change, before anything can be sent. It *clears* rather than writing an empty `Configuration`: a client-authored `{choices: {}, statuses: {}}` is truthy and would beat the `or empty_configuration()` fallback in `configuration.py`, leaving the canvas with no option statuses. The adapter builds the run input by *picking* keys off frontend state, so a cleared state yields an input with no `configuration` key, and LangGraph keeps absent channels at their checkpointed values — verified against the running server rather than only read. Message hydration is display-only, because LangGraph resumes runs from its own checkpoint regardless. State hydration isn't: what the frontend holds is what the next run starts from.

The thread history endpoints return 500, not 404, for a thread the server has never seen, so any non-OK response is treated as "brand-new thread, nothing to restore". Runs then write through to the store on the agent side, which demotes the checkpoint to a historical record with no LangGraph-side change.

## Staleness across conversations

The attachment hook compares the reopened thread's checkpoint `configuration` with the workspace's current one, using a key-order-independent stringify because the two take different serialization paths. On mismatch it flags the thread stale through `StaleThreadContext`, exported from `card-dispatch.ts` and defaulting to `false` so cards outside a workspace are unaffected, and `useCardDispatch` treats the flag like its existing inert conditions. Within-thread staleness behavior is unchanged.

*The three inert conditions aren't equally self-explanatory, and the card shipped treating them as if they were.* The fix was built with [parallel-drafts](../parallel-drafts/design.md), which made the sentence name both drafts. `CardShell` dims to `opacity-60` and says nothing, which is enough for the two conditions the transcript already accounts for — the card the operator just clicked, and the card a later message has overtaken — and not enough for the third, where the cause is outside the conversation entirely. So `CardShell` takes an optional reason and renders it as a line inside the card, and the other two paths pass nothing and look exactly as they did. The line is the operator's half of what the shared-attention context entry already tells the agent, in `src/app/workspaces/[id]/page.tsx`: the agreement was changed in another conversation after this transcript's last turn. Nothing about which cards are inert changes. This is what makes the existing rule legible, and it is deliberately a line of text rather than a banner, because the confusion happens at the control the operator tried to use.

Carrying the reason costs one type change. `StaleThreadContext` was a boolean, and nothing downstream of it knew anything but that, so it becomes the *reason itself* — a formatted string, or `null` for a thread that is current — with `useCardDispatch` returning it beside `inert` and computing `inert` from it as it did from the flag. The string is formatted where staleness is decided, in the attachment hook, which keeps `card-dispatch.ts` knowing that a conversation can be superseded without knowing what supersedes it. The default has to stay falsy so cards rendered outside a workspace are unaffected, which is what `false` bought; `null` buys the same, and an empty object wouldn't.

## System prompt

Two additions. The agreement may have been changed in other conversations, so trust the current state from `get_configuration` over the transcript when they disagree. And the naming instruction from *Terminology and naming*: name the elevator through `name_workspace` as identity emerges, and never ask the customer for a name.

## Testing

Store: unit tests in `agent/tests/test_workspace_store.py` cover the create, read and save round trip, thread registration idempotence, recency ordering, and rejection of unknown ids and path escapes. Deletion adds two: that it destroys the record and leaves every other workspace where it was, and that it refuses a second delete, an unknown id and a path-like one. `agent/tests/test_http_app.py` covers the route — delete, then the list without it, then 404 from both `GET` and a second `DELETE`. The delete control itself is seen by no check: it is UI, and the tier that renders the frontend's stateful middle covers attachment rather than the list page. The whole path was exercised through the running dev server with `curl` — create, delete, and 404 from a later `GET` and a second `DELETE`, through the Next rewrite the browser uses — and both pages still serve. What that does not reach is the standing gap: no browser could be attached in the session this was built in, so the dialog, the restructured list row and the claim that the control mounts after hydration without shifting a `useId` are unverified by anything but the rule they were written to. Run the app and confirm those before trusting them. Agent: the existing pure-function tests are unaffected, 77 passing.

Renaming adds three route checks in `agent/tests/test_http_app.py` — that a rename writes the trimmed name and answers with the record, that an empty one is a 400 with the old name still standing, and that an unknown id is a 404 — and five in `tests/interface/rename-elevator.test.tsx`, which is the first frontend check of either of these two controls: that the field opens on the name and empty on an unnamed elevator, that a rename reaches the store and reports back the name the store kept, that confirming an empty name leaves the control operable and asks the store for nothing, and that a failed rename keeps the name and says so in text the field points at. What no check sees is the mirror correction above, because it needs a conversation in which the agent has named the elevator: verify it by running the app, letting the agent name an elevator, renaming it from the canvas head, and confirming the head shows the operator's name and `get_configuration` reports it.

*Browser pass* (constitution #9), run 2026-08-31 against `npm run dev`. From the elevator list: every row draws the control, labelled *Rename “…”* where there is a name and *Name this elevator* where there is not; the field opens empty on an unnamed elevator; confirming an empty name leaves both buttons operable, asks the store for nothing and answers with the `sayWhy` sentence; a real rename trims, writes, and the re-read row shows the stored name. The overlay was checked with a real pointer rather than a scripted click, because a scripted one ignores hit-testing and so proves nothing about stacking: a pointer on the pencil opens the field and focuses it without navigating, and a pointer on the name still opens the elevator. From the head of an open agreement: the field opens on the current name, the breadcrumb shows the new one the moment the store answers, and a later `GET` agrees. No console error and no hydration warning on either surface, across two consecutive loads — the second being the one that counts under `next dev`. What the pass did not reach is the live mirror case above, which needs an agent turn that calls `name_workspace`.

Frontend and journey: a browser pass per constitution #9 ran create → converse, with choices and candidate persisted to the store → cold reload showing the canvas with no conversation → a canvas edit starting and registering a conversation and writing through → reopening the first conversation, where the transcript hydrates and the canvas keeps *current* state → "where were we?" answered from current state rather than the transcript. The same pass dragged the split to both floors, and checked the stacked orientation, both themes, and the absence of hydration errors.

Two known gaps came out of that pass. Card inertness in stale threads is wired and typechecked but was never exercised, because the test transcripts carried no cards; exercise it when a card-bearing conversation gets superseded. And a reopened transcript once showed an assistant message with its text duplicated, most likely a hydration or serialization quirk inherited from the resumption machinery, cosmetic and not chased.
