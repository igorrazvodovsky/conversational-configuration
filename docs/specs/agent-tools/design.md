# Agent tools — design

Rules the agent's tool surface: the state schema in `agent/src/configuration.py`, what each tool may mutate, and how state streams to the UI. It also holds the one-home-per-instruction rule, so read it before adding or changing a tool, and before deciding where a new instruction to the agent belongs.

## Shape

`agent/src/configuration.py`:

- Module-level `MODEL = load_model(...)` and `SOLVER = ConfigSolver(MODEL)` give one solver session for the process lifetime, matching the persistent-session design of the [solver service](../solver-service/design.md).
- `AgentState` gains a `configuration` key, with the schema the requirements set. The todo state and tools are unregistered from `main.py`, and the example files stay in the repo untouched as CopilotKit reference material.
- Pure functions `apply_choices(config, choices, source)`, `withdraw_choices(config, vars)` and `make_candidate(config)` take and return plain state dicts, so the `@tool` wrappers around them stay thin, mirroring the Command-update pattern of `manage_todos`. Unit tests target the pure functions, and nothing mocks ToolRuntime.
- Every tool that moves the agreement returns through `_committed`, which takes the action's name and whose move it is as keyword-only arguments with no defaults, because the runtime carries no tool name and an entry of the draft's log has to say which action wrote it ([action-log](../action-log/design.md)). A new committing tool that omits them raises at its first call rather than logging anonymously, and `CONTENT_ACTIONS` is the set of names an entry may carry.

## Tools

- `set_choices(choices: dict[str, str], source: "user" | "agent")` returns, on success, `Command(update={"configuration": ...})` with a ToolMessage listing newly forced values. On conflict it updates no state, and the ToolMessage carries `Conflict.describe()` plus the structured ids, so the LLM can negotiate.
- `clear_choices(variables: list[str])`.
- `propose_completion(objective="price" | "co2")` stores `{assignment, price, footprint}` as the candidate and returns it. Under the [service-agreement spec](../service-agreement/design.md), `price` means EUR/month — the key name is kept for thread-resumption compatibility — and the message presents a service agreement over its term. Under the [environmental-footprint spec](../environmental-footprint/design.md) the other objective is always solved too: when the two assignments differ, the message appends how many variables differ and both deltas, so the trade-off is disclosed at the moment of proposal.
- `get_configuration()` is a read-only echo of state for the LLM. Statuses are summarized to non-open facts only, to keep tokens down.
- `describe_product()` returns variables, groups, option labels and prices from the model, so the LLM never invents the catalog. Every price it prints is EUR/month — agreement fees directly, hardware as amortized deltas at the default term — so the LLM never sees a capex figure it could leak. Options also carry their embodied CO₂e delta, after the fabrication multiplier, so quoted figures reconcile with candidate totals. The output ends with the assessment-assumptions section from the model's `footprint` block, which grounds every footprint number the agent states in chat ([environmental-footprint](../environmental-footprint/design.md)).

## System prompt

The prompt is built around the elicitation strategy: needs-first questions, record every choice as it is made, announce forced values, surface conflicts with the rule labels verbatim, offer a priced candidate early and refine by critique. One prohibition is explicit: never claim feasibility or infeasibility without a tool result.

Under the [service-agreement spec](../service-agreement/design.md) the frame is a service agreement. Elicitation targets the building and its outcomes — traffic, budget per month, uptime, commitment length — candidates are presented as "€X/month over the N-year term", and a second prohibition applies: never quote a one-off capex figure.

The [environmental-footprint spec](../environmental-footprint/design.md) adds the claims discipline. Footprint figures come only from tool results, always as "modelled, under these assumptions"; the energy class is never presented as certified; the vocabulary excludes "green", "eco-friendly" and "sustainable"; and the pair the two objectives give — the cheapest completion and the lowest-footprint one — is offered when the customer signals footprint interest. The four-step frames sequence itself lives in the docstring of `propose_completion`.

*Record before you ask.* The method block orders the two: a term the customer's own words answer is recorded with `set_choices` in the same turn, and only what is still open is asked. The ordering was missing until 2026-08-31, and its absence showed on an opening turn. Told "We're planning a new hotel", the agent called `describe_product` and `name_workspace`, recorded nothing, and raised an `ask_choices` card over installation type, region, building type and usage profile — one of which that sentence had already answered, and one of which recording that answer would have settled, since `building_type=hotel` forces `usage_profile=medium`. "Record every choice as it is made" reads as a rule about choices already extracted and says nothing about what to do before asking, so the turn was framed as asking and never as recording. The equivalent rule for documents was already there — nothing the document settles is asked again — and speech had none.

The rule's example is the building type alone. "A new hotel" reads as a new building and the temptation is to take the installation type from it too, but *new* there modifies the project rather than the shaft: a hotel opening in a converted building is an ordinary case, and installation type is the term that separates the two. A value inferred past what the customer said would be recorded with `source="user"` on words they did not speak, which puts a term on the sheet as the customer's own when they never chose it. So the prompt says to read only what they said and to ask about the rest.

Two things follow from a statement left unrecorded, beyond making the customer answer twice. It is a question put to someone who has already answered, which is the interrogation [showing a candidate works better than asking a sequence of questions](../../discovery/assertions/candidate-works-better-than-questions.md) exists to avoid. And an undecided variable is one a completion may fill with its own pick, so the sheet can go on to assert a residential building the customer never asked for — the same shape as the rejected-batch failure recorded under [the agent proposes and the user decides](../../discovery/principles/agent-proposes-user-decides.md). Nothing on the card said otherwise: had the choice been recorded, `build_ask_payload` would have given it `status: "chosen"` and the card would have drawn it active.

Five headed blocks organize the prompt — method, requirements documents, voice, messages that are not conversation, state — rather than one flat list, so each instruction sits with the others that fire at the same moment.

## Where guidance lives: one home per instruction

Every tool description ships on every request alongside the system prompt, so an instruction stated in both is paid for twice and can drift out of sync. Each is therefore stated once, in the place chosen by *when it has to fire*.

The saving is larger than it looks on paper. Static context fell 14%, from 2,878 to 2,484 tokens, but measured prompt cost fell 24%, from 21.3k to 16.3k tokens per conversational turn, because a turn runs several model calls around the tool loop and every one of them resends the whole prompt.

- *Which tool, and with what arguments*, is read at the moment of the call, so the docstring is the home. That covers `describe_product` before the first `set_choices`, the `source=` semantics, the 1–4 related variables of `ask_choices`, `fork_draft` before a big exploratory change, `switch_draft` when the customer picks one, and the cheapest-and-greenest calling pattern of `propose_completion`.
- *What to write in the reply* is narrative discipline that has to hold across the whole turn, including turns with no tool call at all, so the system prompt is the home. That covers never enumerating options the control already shows, never repeating a card's table or option list, treating repairs as choices rather than verdicts, never announcing a naming, sourcing footprint figures only from tool data, and the one-sentence trade-off line when the objectives disagree.

*Record before you ask* is prompt-side for the same reason. By the time the model reads the `ask_choices` docstring it has already decided to ask, and this rule has to fire before the turn is framed — the case the A/B below found the docstring cannot serve. It is stated in the method block only; the `source=` semantics it depends on stay in the `set_choices` docstring, which the model reads at the moment it records. Its companion — raise the control for what is still open, in the same turn — is the second measured exception to this rule and sits in both places, for the reason under *Testing*.

*One documented exception: revise over record.* "When the customer *tells* you to change something already decided, revise it rather than recording it afresh" is stated in both the `revise_choices` docstring and the prompt's method block, because moving it to the docstring alone measurably broke the flow. In a scripted A/B against gpt-5.4-mini — three runs per arm, identical scenario of a recorded modernization followed by "actually I need 3.0 m/s" — the baseline prompt chose `revise_choices` 3/3 and the customer got clickable repair paths. With the rule in the docstring only, the agent fell back to `set_choices` 2/3, which returns a flat `REJECTED` and no repair options, so [revision is an ordinary move, not a restart](../../discovery/principles/revision-is-an-ordinary-move.md) failed at the moment it matters most. Restoring the four lines took it to 5/5 with cards. The general lesson holds but is narrower than it first looked: the docstring is enough for guidance the model reads while *choosing among tools it has already decided to use*, and not for guidance that has to fire before it has framed the turn as a revision at all.

The bullet now covers *prose only*, and says so, because [one gesture, one action](../one-gesture-one-action/design.md) took the judgment out of the dispatched path: a `Set …` sentence from a control or the sheet reaches `revise_choices` whether or not the term was decided, ruled by the *Messages that are not conversation* bullet rather than by this one. The A/B that justifies keeping the bullet was run on a typed revision — "actually I need 3.0 m/s" — which is exactly the case it still rules, so the measurement survives the narrowing.

The rule covers *static* context only. Runtime tool results still carry their own emphasis: `set_choices` and `revise_choices` label newly forced values "(announce these to the customer)" in the message body, which is contextual and fires only when there is something to announce.

## State streaming

Should `StateItem(state_key="configuration", tool="set_choices", tool_argument=...)` be registered? `StateStreamingMiddleware` streams tool args as they generate, and for configuration the authoritative state comes from the solver-validated Command update, so streaming raw args would flash unvalidated values. Decision: no streaming middleware for configuration. The [agreement-document design](../agreement-document/design.md) revisited and upheld it.

## Notes from implementation

- Deviation from the draft: *all* example tools — todos, a2ui, flight search, query_data — were unregistered from `main.py`, not only todos, because the elevator-focused system prompt would have contradicted their guidance. The example files remain in the repo, and the [agreement-document spec](../agreement-document/design.md) reintroduced a generative-UI path deliberately, as `ask_choices`.
- Smoke-tested against gpt-5.4-mini. "6-storey hotel in Munich, 20 m travel" had the agent record hotel, europe, new_build and mid-travel choices; the rules forced EN 81-70 accessibility and a gearless MRL drive, and it proposed a €61,700 candidate into shared state. "Modernization + 3.0 m/s" produced an atomic REJECTED with R04 and R28, and the agent verbalized the headroom explanation and offered ways forward.
- Rejection was batch-atomic at first: one bad choice refused the whole call, and re-recording the innocent subset was left to the model. It didn't do that, which is what the rework addresses.
- What a rejection costs was reworked after the prototype walkthrough of 2026-08-20 found it costing too much. `set_choices` goes through `record_choices`, which asks the solver for the minimal conflict, declines every member of it that arrived in this batch — all of them, so nothing arbitrary is picked between two things the customer said — retries with the rest, then hands the declined ones back with their rules. The walkthrough's case was an opening turn stating an office in Frankfurt, twelve floors, 25 m of travel and a 1000 kg car. R14 separates that travel band from that stop count, the whole batch was refused, and the completion that followed filled the emptied variables itself, so the sheet went on to describe a residential building with a 630 kg car. Choices already recorded are never declined: a new choice that collides with an agreed one is the one refused, and the agent is told to reach for `revise_choices` there, which is where repair paths live. This partial contract is what a *prose* batch gets. A dispatched batch does not: [one gesture, one action](../one-gesture-one-action/design.md) sends every `Set …` sentence to `revise_choices`, so the same five values arriving from a form card refuse whole rather than half-landing, on the ground that the customer picked each of them deliberately.
- A change no longer un-prices the agreement. `_repriced` completes again on the previous candidate's objective whenever a transition invalidates it, inside the same batch, so one undo still reverses one step. In the same walkthrough, a click on a cabin finish took the sheet from a monthly fee to "No priced proposal yet". An agreement with no candidate is left alone, since `propose_completion` is still what asks for a price. The reprice passes the previous assignment to the solver as a tie-break, `complete(..., prefer=…)`: cost-free variables leave many equally optimal completions, and re-solving from scratch flipped car height, shaft size and pit depth on a cabin-finish edit, which the canvas would then have marked as changes nobody asked for. The preference is the last objective declared, so it decides between optima and never buys a worse price or footprint.
- Rules travel with state. `Configuration.unavailable` is a variable → value → named-rules map covering every option that can't be taken, built beside `statuses` by `_derived` and rebuilt on restore. `get_configuration` reports the rules behind each forced value from it, which is what lets the agent answer "why is this here?" by quoting the model (constitution #6) rather than reconstructing a reason — the walkthrough caught it composing a correct but unsourced account of the accessibility package. The cost is one `valid_options` per decided variable plus one `explain` per unavailable option, and it stays flat as an agreement fills up: a whole transition, statuses, rules map and reprice together, measured 0.29 s at twelve recorded choices and 0.35 s at nineteen, with roughly seventy unavailable options either way.

## Verification of the de-duplication

Measured against the pre-de-duplication prompt with a scripted A/B: six scenarios, three runs per arm, eighteen completed conversations each side. Every scorable behavior came out identical — call order, `source="user"`, `revise_choices` on a revision, no options enumerated where a control was shown, empty text after a clean canvas edit, the workspace named without announcing it, no prohibited vocabulary, no untraceable footprint figure. The first pass found the one regression recorded earlier; a full re-run after the fix showed no remaining difference, and `tests/compare_refs.py HEAD` reproduces that result through the permanent harness ([conversation checks](../conversation-checks/design.md)).

Known gap: this evidence is all about single moves. Nobody has made a manual pass over the [demo scenarios](../../discovery/scenarios/) — a whole conversation's arc, resumption, the RFQ entrance — and nothing automated would catch an agent that merely grew vaguer over twenty turns.

## Testing

`agent/tests/test_configuration.py` covers the pure functions: apply, conflict rejection and forced reporting; withdraw with candidate invalidation; and candidate correctness, meaning it extends the choices, is solver-valid, and its price matches. Chat-level behavior is exercised by hand through `npm run dev` and by the [conversation checks](../conversation-checks/design.md).

No free check sees a prompt edit, so *record before you ask* was measured with a scripted A/B on the one turn it rules: HEAD against the edit, four runs an arm against gpt-5.4-mini, the single message "We're planning a new hotel". At HEAD the building type was recorded in three runs of four and put back to the customer as a question in two of four; the run that recorded nothing asked over six variables at once, which is the reported failure exactly. With the rule, four of four recorded `building_type=hotel` with `source="user"` before anything else and none asked it back, and five further runs after the docstring change below held that at five of five. The harness is `tests/scenario_runner.py` driven by a throwaway script rather than a scenario: one turn, both arms in one process over one solver, and the baseline agent built by executing HEAD's `main.py` in its own namespace, so no file is swapped on disk to run an arm.

*What the A/B also found: invented variable names.* In both arms the agent reached `ask_choices` without having called `describe_product` first and passed names the model does not define — `floors`, `traffic_profile`, `budget_monthly`, `uptime_target`, `floors_or_height`. The tool refuses them and hands back the valid list, so nothing is corrupted, but the customer gets no card: across the eight A/B runs three turns ended with the agent asking in prose for values a control was meant to carry. `describe_product` said "call this before you first record or change anything", and asking is neither. It now says record, change *or ask*, and states that a variable name not read there does not exist; `ask_choices` names it as the source of its own argument. Over the five runs measured at that point `describe_product` came first in all five and every name passed was real; later samples had it skipped twice, always on a turn that then ended in prose, and the final six have it first in all six. Those runs exercise the elicitation entrance only; the document entrance, where the prompt already orders `describe_product` then `ingest_rfq`, was not re-run, and the edit can only make the call it already requires more likely.

*A question left standing in prose.* Recording first exposed the next fault rather than causing it: in two of those five runs, and in one HEAD run, the agent recorded the hotel and then asked in prose — "next I need the region and whether this is a new build or a modernization" — with no control behind it. "When you want the customer to pick something, call ask_choices" did not reach it, because the agent did not read *naming a term it needs* as wanting the customer to pick. The bullet now says so and closes the turn: a turn that says it needs a value from the customer ends with the control for it, and never leaves that term standing as a question in prose. It exempts one thing by name — inviting critique of a proposal asks for a reaction, not for a value — because an unqualified prohibition would put a card after every completion, which is the question sequence [showing a candidate works better than asking a sequence of questions](../../discovery/assertions/candidate-works-better-than-questions.md) exists to replace. Six runs after that edit put every ask inside a card's reach — real names, within the limit — where the runs before it had ended in prose.

*The cap, measured in the same runs.* With the question forced into a control the cards grew: five, seven and eight variables at once, reaching `rated_load`, `rated_speed` and `accessibility` on an opening turn that had no decision resting on any of them. `ask_choices` had said "1-4 related ones at a time" since it shipped and nothing enforced it, so `build_ask_payload` now refuses a fifth with a message naming the limit, the way it already refuses an unknown name — `ask_choices` is its only caller and turns both into an `ERROR:` the agent can act on. It is the documented contract made to hold, not a new rule, and `test_payload_refuses_more_than_one_card_asks` carries it; no live run has exercised the refusal, because the docstring kept the asks inside the limit. The six runs after it asked two to four variables each, all real names, no errored call.

*A budget is not a variable.* The same runs had the agent asking for one — `budget_cap`, `budget_monthly`, `budget per month` — and being refused, because no variable holds a monthly ceiling; `budget_cap` exists only as a field on an ingested RFQ, compared against the candidate's price by `_budget_lines`. The Method block listed budget per month among what to elicit and said nothing about where it goes, so the bullet now says: a budget steers what you propose rather than being recorded or asked for. Both refusal messages also end in an instruction now — "ask again with names from that list", "ask again with those" — because a run that was refused once gave up and answered in prose instead of retrying.

*What it took to hold at six of six.* The bullet alone did not settle it. After the wording was narrowed for the critique exemption, one run in six still ended in prose, and a variant forbidding the agent to list the terms it needed in words made it worse — three of six — because a prohibition with no move to make left it nowhere to go. What held was a sentence in `set_choices`'s own docstring: having recorded what the customer told you, raise `ask_choices` in the same turn over the terms you need next, since a turn that ends in prose asks them to type what a control would have taken. Six of six after that, every one `describe_product` → `set_choices` → one `ask_choices` over two to four real names, no refusal. The docstring was rewrapped afterwards; the six runs measured the unwrapped form, which differs from it in line breaks only. It is a second deliberate duplication with the prompt, on the same ground as revise over record and with the same kind of measurement behind it: the prompt frames the turn, and the docstring fires at the moment the model has just recorded and is choosing what to do next.

One residual, once in six: a card that includes a term the rules have already forced, which shows one live option and the rest struck with their reasons. It is a poor question rather than a wrong one, and the `ask_choices` docstring now says a forced term is not one; nothing enforces that, because a card over a settled term is exactly how a customer asks to see why it is settled. All of this is one turn type measured many times. The strengthened bullet fires on every turn, and nothing here exercised a mid-conversation ask, a canvas edit or the document entrance; `pytest -m scenario` is what would.
