# Conversational product configuration

A research prototype: chat-based configuration of a complex industrial product (an elevator), built on CopilotKit v2 + LangGraph. Next.js frontend at the repo root, Python agent in `agent/`.

## Development method: discovery-framed, spec-anchored

Everything written lives under `docs/`, in two layers. Discovery (`docs/discovery/`) frames the design problem and sets direction, after Dan Brown's *Practical Design Discovery*. Specs (`docs/specs/`) execute against that direction. Non-negotiable workflow:

1. Read `docs/specs/constitution.md` before making changes — its principles override convenience. For anything touching the interaction design, also read `docs/discovery/brief.md`.
2. Any change that adds a capability, changes behavior, or makes an architectural choice needs a spec in `docs/specs/<feature-name>/`: `requirements.md`, `design.md`, and — while the change is in flight — `tasks.md`. Write or update it *before* implementing; a new feature needs user approval of `requirements.md` first. Bug fixes and mechanical changes need no spec. Feature directories are named, not numbered, and are cited by name: `the [nonlinear-interaction spec](…/specs/nonlinear-interaction/requirements.md)`.
3. Every new spec cites the discovery principle or assertion it serves by linking that note, with the principle's own words as the link text — `Serves discovery principle [trade-offs are shown as a pair](…/principles/trade-offs-shown-as-a-pair.md)`. Never cite by code or by section number. One file each in `docs/discovery/principles/` and `docs/discovery/assertions/`. A spec that serves none is a signal the framing is stale — fix the framing, don't skip the citation.
4. After implementing, reconcile `requirements.md`/`design.md` with what was actually built and retire `tasks.md` — its durable residue (verification record, known gaps, deviations from the plan) moves into `design.md`; the plan's history stays in git. A spec that disagrees with the code is a bug. Discovery artifacts are living too: when work changes the framing or direction, update them in the same session.
5. Indexes: features and roadmap in `docs/specs/README.md`; the current discovery cycle and its open questions in `docs/discovery/phase-plan.md`; the evidence base in `docs/research/`, with what it still lacks in `docs/research/gaps.md` — check there before proposing more research.

## Gotchas

*Dead starter code.* The repo began as the CopilotKit todo/A2UI starter and the example files are still here, unused by the configurator: `src/components/example-canvas/`, `src/hooks/use-generative-ui-examples.tsx`, `use-example-suggestions.tsx`, `src/components/generative-ui/{charts,meeting-time-picker.tsx}`, `agent/src/{todos,query,a2ui_fixed_schema,a2ui_dynamic_schema}.py`, `agent/src/a2ui/`, `agent/src/db.csv`. Keep them as CopilotKit reference; don't extend them and don't read them as current behavior. `src/app/declarative-generative-ui/` is starter code too, but it is still mounted as the A2UI catalog in `layout.tsx` — dead from the agent's side, live from React's. `README.md` is likewise the upstream starter's readme: its install/run/scripts sections are correct, its framing and structure diagram describe the todo demo and are not.

*Running it.* `npm run dev` — UI on 3000, agent on 8123, plus a `dev:infra` step that runs first. Constitution #9 makes this the only verification UI and conversation get.

*What's live.* `agent/main.py` (system prompt) → `agent/src/configuration.py` (state schema + tools) → `agent/src/solver/` (Z3) over `agent/src/product_model/elevator.json`; durable agreements in `agent/src/workspace_store.py` (JSON under `agent/data/workspaces/`, gitignored) served by `agent/src/http_app.py` mounted via `langgraph.json`. Frontend: `src/app/page.tsx` (workspace list) → `src/app/workspaces/[id]/page.tsx` → `src/components/workspace/` (canvas and chat in resizable panels, no third column: the conversation list is in the chat's header, the workspace's name and back link at the head of the canvas), `src/components/config-canvas/`, and the in-chat cards in `src/components/generative-ui/`. The canvas is a three-layer agreement document — recitals prose, numbered operative terms, collapsed hardware schedules — not a flat sheet; the layer mapping and the prose templates are frontend-side, and every layer edits through one `OptionEditor` and the shell's routed dispatch (`docs/specs/agreement-document/design.md`).

*Shared agent state.* State lives in the agent (constitution #3), not in React. `AgentState.configuration` is defined in `agent/src/configuration.py`; tools mutate it by returning `Command(update={"configuration": ...})`; the frontend reads `agent.state.configuration` and writes `agent.setState(...)` via `useAgent()`. There is no frontend store to keep in sync — adding one is a constitution violation.

*Conversation ≠ configuration.* A workspace (one per installation) is the durable home of the agreement; conversations are ephemeral views onto it, several per workspace. Tools write through to the workspace store; the thread checkpoint is only a historical record, and `src/hooks/use-workspace-attachment.ts` enforces that on attach. That hook is trap-dense — tool-call shape conversion, the connect wiping or overwriting hydrated state, the agent instance swapping identity — all in `docs/specs/agreement-workspace/design.md`; read it before touching the hook.

*Cards are messages, not callbacks.* Tools that render UI return a JSON payload with a `kind` field; clicking a card dispatches a visible structured user message (`Apply repair: …`, `Adopt frame "…"`) that the agent maps onto one atomic tool call — shared staleness and dispatch behavior in `src/components/generative-ui/card-dispatch.ts`, shared shape (props, pending row, card box, payload check) in `card-shell.tsx` beside it. Agent prompt wording and card copy are therefore coupled; change them together. Exception: direct canvas edits use the same grammar prefixed `Canvas edit: ` and are *hidden* from the chat (filtered in `src/components/chat/message-view.tsx`), with the agent prompted to reply with empty text on a clean apply — the sheet is the record, the chat carries only consequences (`docs/specs/agreement-document/design.md`). A third prefix, `Reconcile deviation: `, is visible again and maps onto `reconcile_requirement` (`docs/specs/rfq-reconciliation/design.md`): answering a requirement of the customer's own document is negotiation, not bookkeeping. The canvas picks between the last two *per variable* — a term the RFQ speaks to reconciles, every other one edits — so the same click means different things on one document, wherever in it the click lands. The canvas's own chrome dispatches two more visible sentences, *Undo the last change* and *Redo the undone change*, onto `undo_change` / `redo_change` (`docs/specs/undo/design.md`); the history they walk lives on the workspace record, written by `save_configuration`, and agent state carries only a depth mirror the controls render from.

*UI components.* Every configurator surface is built from shadcn/ui in `src/components/ui/`, installed with `npx shadcn@latest add` and never hand-written; reach for a primitive before writing a `className` string. Do not run `shadcn init` — it authors `globals.css` wholesale and would lose several things it knows nothing about. Three things in that stylesheet fail *silently* if disturbed: the `@theme inline` bridge (without it `bg-primary` is not a class at all, with no error), the `shadcn/tailwind.css` import, and the zero radius ramp — which only holds because literal `rounded-*` classes were also stripped at the call sites. A few upstream defaults are deliberately relaxed at call sites. All of this, and the reasons, are in `docs/specs/ui-component-library/design.md`.

*The chat pane* follows the same rules, composed from `CopilotChat`'s slots in `src/components/chat/` — never by patching the package or selecting into its markup. It is trap-dense in its own way (a replaced scroll view owns the composer clearance and the landing position after hydration; message elements are not one-per-message); read the design decisions in `docs/specs/chat-pane/design.md` first.

*The workspace page's tree* has two rules, both from `docs/specs/chat-surface/design.md`. Nothing that mints a React id may join the *hydrated* tree — a Radix menu there shifts `useId` values page-wide and breaks hydration on every load, so the chat header's two menus — mode and conversations — both mount a tick later. Inserting a plain component above id-minting descendants does it too: factoring the canvas's three identical layer headings into a `<LayerHeading>` broke hydration on every load until the duplication was shared as a class string instead (`docs/specs/agreement-document/design.md`). Share markup here as classes, not as components. And the chat is mounted exactly once, its four geometries (sidebar, floating, full screen, hidden) expressed as classes, because re-parenting it resets the transcript's scroll. A third rule follows from those: `useAgent()` re-renders its caller on every streamed token, so nothing on the page itself may call it — the header's unread watcher and the suggestion strip's `SuggestedMoves` both subscribe from leaves that draw two buttons and nothing at all respectively. One standing exception predates the rule and is not covered by it: `useWorkspaceAttachment` calls `useAgent()`, and the page calls that hook, so the page does re-render per token as things stand. Read that as a violation still to be unpicked rather than as permission to add a second one — each subscription pushed into a leaf is one less thing to move when it is. Beware a false positive when checking the first rule: under `next dev`, the first page load after an edit reports a hydration mismatch, and the next load with the same code is clean. It is the dev server's own inconsistency, not the page's — the server HTML is byte-stable across the edit, a bare `<div>` reproduces it, and a production build shows nothing. Reload before believing one.

*Python.* uv in `agent/`, npm at the root. `uv run pytest` for solver and state-transition tests; `uv run python src/product_model/validate.py` to check the product model. UI behavior has no automated check — verify by running the app.

*Conversation checks.* `uv run --env-file ../.env pytest -m scenario` runs the demo scenarios against the live agent; `uv run --env-file ../.env python tests/compare_refs.py <ref>` runs them against two checkouts and reports which assertions moved — the only check that sees a system-prompt or docstring edit at all. Both cost money and are deselected from the default suite. Assertions read tool calls, payloads and state, never prose; that position is measured, not assumed, and the harness's traps (per-call `WORKSPACE_STORE_DIR`, sequential arms) are in `docs/specs/demo-scenarios/design.md`.

*Model.* The agent runs OpenAI `gpt-5.4-mini` with `parallel_tool_calls` disabled (`agent/main.py`). No spec records why parallel calls are off — treat it as deliberate (the card-click flow assumes one atomic tool call per message) until someone verifies otherwise.

## Writing style

- Banned phrases: "load-bearing", "worth stating plainly", "full stop",
  "carry the argument", "the trap", "isn't just X — it's Y".
- No punchy fragments for drama. Write complete sentences.
- Do not build to a turn of phrase. State the claim directly.
- Technical documentation, not marketing copy.
