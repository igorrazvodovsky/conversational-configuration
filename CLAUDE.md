# Conversational product configuration

A research prototype: chat-based configuration of a complex industrial product (an elevator), built on CopilotKit v2 + LangGraph. Next.js frontend at the repo root, Python agent in `agent/`.

## Development method: discovery-framed, spec-anchored

Everything written lives under `docs/`, in two layers. Discovery (`docs/discovery/`) frames the design problem and sets direction, after Dan Brown's *Practical Design Discovery*. Specs (`docs/specs/`) execute against that direction. Non-negotiable workflow:

1. Read `docs/specs/constitution.md` before making changes — its principles override convenience. For anything touching the interaction design, also read `docs/discovery/brief.md`.
2. Any change that adds a capability, changes behavior, or makes an architectural choice needs a spec in `docs/specs/<feature-name>/`: `requirements.md`, `design.md`, and — while the change is in flight — `tasks.md`. Write or update it *before* implementing; a new feature needs user approval of `requirements.md` first. Bug fixes and mechanical changes need no spec. Feature directories are named, not numbered, and are cited by name: `the [nonlinear-interaction spec](…/specs/nonlinear-interaction/requirements.md)`.
3. Every new spec cites the discovery principle or assertion it serves by linking that note, with the principle's own words as the link text — `Serves discovery principle [trade-offs are shown as a pair](…/principles/trade-offs-shown-as-a-pair.md)`. Never cite by code or by section number. One file each in `docs/discovery/principles/` and `docs/discovery/assertions/`. A spec that serves none is a signal the framing is stale — fix the framing, don't skip the citation.
4. After implementing, reconcile `requirements.md`/`design.md` with what was actually built and retire `tasks.md` — its durable residue (verification record, known gaps, deviations from the plan) moves into `design.md`; the plan's history stays in git. A spec that disagrees with the code is a bug. Discovery artifacts are living too: when work changes the framing or direction, update them in the same session.
5. Name behavior by the ontology (constitution #15). `docs/specs/ontology-of-phenomena/ontology.md` enumerates the prototype's individuals, values, actions and facts, and every spec, prompt paragraph, tool signature, card sentence and check names a happening by its name there. Adding or removing a tool, a state key, a store mutation or a card sentence means reconciling that file in the same session. It describes rather than renames: names already persisted stay, and realigning one is its own change. The places where the artifacts currently disagree are recorded at the end of it.
6. Indexes: the feature register in `docs/specs/README.md`; the current discovery cycle and its open questions in `docs/discovery/phase-plan.md`; the evidence base in `docs/research/`, with what it still lacks in `docs/research/gaps.md` — check there before proposing more research. Inside a feature the third line routes: `requirements.md` opens on a `Status:` line, `design.md` on one naming what it rules and the change that should send you to it.

## Gotchas

*What's live.* `agent/main.py` (system prompt) → `agent/src/configuration.py` (state schema + tools) → `agent/src/solver/` (Z3) over `agent/src/product_model/elevator.json`; durable agreements in `agent/src/workspace_store.py` (JSON under `agent/data/workspaces/`, gitignored) served by `agent/src/http_app.py`, mounted via `langgraph.json`. Frontend: `src/app/page.tsx` (workspace list) → `src/app/workspaces/[id]/page.tsx` → `src/components/workspace/` (canvas and chat in resizable panels, no third column: the conversation list is in the chat's header, the workspace's name and back link at the head of the canvas), `src/components/config-canvas/`, and the in-chat cards in `src/components/generative-ui/`.

*Dead starter code.* The repo began as the CopilotKit todo/A2UI starter and the example files are still here, unused by the configurator: `src/components/example-canvas/`, `src/hooks/use-generative-ui-examples.tsx`, `use-example-suggestions.tsx`, `src/components/generative-ui/{charts,meeting-time-picker.tsx}`, `agent/src/{todos,query,a2ui_fixed_schema,a2ui_dynamic_schema}.py`, `agent/src/a2ui/`, `agent/src/db.csv`. Keep them as CopilotKit reference; don't extend them and don't read them as current behavior. `src/app/declarative-generative-ui/` is starter code too, but it is still mounted as the A2UI catalog in `layout.tsx` — dead from the agent's side, live from React's. `README.md` is likewise the upstream starter's readme: its install/run/scripts sections are correct, its framing and structure diagram describe the todo demo and are not.

*Shared agent state.* State lives in the agent (constitution #3), not in React. `AgentState.configuration` is defined in `agent/src/configuration.py`; tools mutate it by returning `Command(update={"configuration": ...})`; the frontend reads `agent.state.configuration` and writes `agent.setState(...)` via `useAgent()`. There is no frontend store to keep in sync — adding one is a constitution violation.

*Conversation ≠ configuration.* A workspace (one per installation) is the durable home of the agreement, held as several *drafts* of it with exactly one current — each a whole configuration with its own provenance, candidate and log of the actions taken on it (`docs/specs/parallel-drafts/design.md`, `docs/specs/action-log/design.md`). Conversations are ephemeral views onto the workspace, several per workspace, and are not pinned to a draft; every tool acts on the current one, so `AgentState.configuration` is always the current draft's. Tools write through to the workspace store; the thread checkpoint is only a historical record, and `src/hooks/use-workspace-attachment.ts` enforces that on attach. Before touching that hook, read `docs/specs/agreement-workspace/design.md`: run-initial-state semantics were assumed to be enough and four further mechanisms proved necessary, none of them obvious from the code.

*Cards are messages, not callbacks.* Tools that render UI return a JSON payload with a `kind` field; clicking a card dispatches a structured user message that the agent maps onto one atomic tool call — visible where it carries a negotiation, hidden where it only sets a value. Agent prompt wording and card copy are therefore coupled; change them together. Shared staleness and dispatch behavior live in `src/components/generative-ui/card-dispatch.ts`, shared shape (props, pending row, card box, payload check) in `card-shell.tsx` beside it. The sentences, and where each is ruled:

- `Apply repair: …`, `Switch to draft "…"`, and the canvas head's fork, switch, compare and discard — visible, one tool each (`docs/specs/parallel-drafts/design.md`).
- `Set <term> to <value> (term=value)` and `Canvas edit: Set …` — one `revise_choices` call each, whether or not the term was decided, so a picked change applies whole or comes back with repair paths (`docs/specs/one-gesture-one-action/design.md`). Both forms are *hidden* from the chat, matched by `isGesture` in `src/lib/configurator.ts` and filtered in `src/components/chat/message-view.tsx`: a sentence that only sets a value leaves no row, because the surface that dispatched it — the sheet, or the card, which reads its own answer back out of the transcript — is the record of it. Only the sheet's edit takes the agent's wordless reply with it, the agent being prompted to reply with empty text on a clean apply; a pick is answered in words, and the tool row after one stays (`docs/specs/agreement-document/design.md`).
- `Reconcile deviation: …` — visible again, onto `reconcile_requirement`, because answering a requirement of the customer's own document is negotiation, not bookkeeping (`docs/specs/rfq-reconciliation/design.md`). The canvas picks between this and a canvas edit *per variable* — a term the RFQ *asks something of* reconciles, every other one edits, a term it speaks to without asking anything included — so the same click means different things on one document, wherever in it the click lands. The document behind it is one list of clauses with identity, and which of `carries` and `requires` a clause holds is what kind it is: a requirement, a clause left to us, or one no variable carries (`docs/specs/document-clauses/design.md`).
- *Undo the last change* and *Redo the undone change*, onto `undo_change` / `redo_change`. What they walk is an append-only log of typed actions over named facts, on the current draft rather than on the conversation, and a reversal inverts one entry's delta rather than restoring a stored state (`docs/specs/undo/design.md`, `docs/specs/action-log/design.md`). A tool that commits names the action it is; `CONTENT_ACTIONS` in `agent/src/configuration.py` is the set an entry may carry, and `tests/couplings.test.ts` holds it against the ontology.

*The canvas* is a three-layer agreement document — recitals prose, numbered operative terms, collapsed hardware schedules — not a flat sheet; the layer mapping and the prose templates are frontend-side, and every layer edits through one `OptionEditor` and the shell's routed dispatch (`docs/specs/agreement-document/design.md`). Its second mode is a three.js render of the configured car in `src/components/config-canvas/render/`, a pure projection of the same live values that draws nothing the agreement does not state. Read `docs/specs/visual-configuration/design.md` before changing either mode; it rules the mounting, the materials and the viewpoints.

*How a state is expressed.* Constitution #16 rules which channels may carry meaning, stated as prohibitions because that is how they apply at a call site: opacity may not carry a state (it composes multiplicatively and no call site can see what it will be multiplied by), hover may not be the only route to a reason or a control, a line style may not be the only difference between two meanings, and neither may colour. What replaces each is a token or a sentence. Reading matter is 14px and chrome is 12px, with nothing below; a refusal is visible text under the control that refuses, through `RefusalList` in `src/components/refusals.tsx`, with `aria-describedby` pointing at it. `tests/legibility.test.ts` holds the two mechanical halves of that. This vocabulary's share of it — the two sizes, the focus indicator, what unavailable and inert look like, and the contrast method behind all of them — is `docs/specs/ui-component-library/design.md`, decisions 3, 5 and 8. Read those before expressing a state as a fade, putting an explanation on a `title`, revealing something on hover, or adding a text size. No spec owns the rule and none is exempt.

*Nothing is disabled to mean no.* Constitution #17: a control that cannot do what it looks like it does stays live, takes the click, and says why — through `sayWhy` in `src/lib/say-why.ts`, a `sonner` toast mounted once in `layout.tsx`. A ruled-out option is the case it exists for: it is muted, struck and clickable, and asking for it dispatches the same `Set …` sentence any other option does, so the repair paths come back (`docs/specs/one-gesture-one-action/design.md`). Two things are still disabled and neither is a refusal — a spent card's controls, because the turn is over and the card is the transcript's record of it, and nothing else; a non-idempotent action guards itself in its handler and shows a spinner. The canvas answers a run in flight once, in the shell's own `dispatch`, which is why no control on the sheet carries the condition. `tests/interface/refusals.test.tsx` holds all four refusing controls against this. The chat composer's send button is the one place the rule reaches into CopilotKit: its `disabled` is computed by the library and intercepted in `src/components/chat/composer.tsx`, which is a coupling to a library internal and is recorded as `docs/specs/chat-pane/design.md` decision 10.

*UI components.* Every configurator surface is built from shadcn/ui in `src/components/ui/`, installed with `npx shadcn@latest add` and never hand-written; reach for a primitive before writing a `className` string. Do not run `shadcn init` — it authors `globals.css` wholesale and would lose several things it knows nothing about, three of which fail *silently*: the `@theme inline` bridge, the `shadcn/tailwind.css` import, and the zero radius ramp. Read `docs/specs/ui-component-library/design.md` before editing that stylesheet or relaxing an upstream default at a call site.

*The chat pane* follows the same rules, composed from `CopilotChat`'s slots in `src/components/chat/` — never by patching the package or selecting into its markup. Message elements are not one per message; read `docs/specs/chat-pane/design.md` before changing the transcript, a row or the composer.

*The workspace page's tree* has standing rules, every one of them measured and recorded in `docs/specs/chat-surface/design.md`. Nothing that mints a React id may join the *hydrated* tree — a Radix menu there shifts `useId` values page-wide and breaks hydration on every load, so the chat header's menus and the canvas's draft switcher all mount a tick later. A plain component inserted above id-minting descendants does it too, which is why the canvas's three identical layer headings are shared as a class string (`docs/specs/agreement-document/design.md`). Share markup here as classes, not as components. The chat is mounted exactly once, its four geometries (sidebar, floating, full screen, hidden) expressed as classes, because re-parenting it resets the transcript's scroll. And `useAgent()` re-renders its caller on every streamed token, so nothing on the page itself may call it — the header's unread watcher and the suggestion strip's `SuggestedMoves` both subscribe from leaves. One standing exception predates that rule: `useWorkspaceAttachment` calls `useAgent()`, and the page calls that hook, so the page does re-render per token as things stand. Read it as a violation still to be unpicked rather than as permission to add a second one. Beware a false positive when checking the first rule: under `next dev`, the first page load after an edit reports a hydration mismatch, and the next load with the same code is clean. It is the dev server's own inconsistency, not the page's — the server HTML is byte-stable across the edit, a bare `<div>` reproduces it, and a production build shows nothing. Reload before believing one.

*Checks.* `uv run pytest` in `agent/`, `npm test` and `npm run typecheck` at the root, all of them run by CI; constitution #9 sets what each tier covers, and `docs/specs/offline-checks/design.md` and `docs/specs/interface-checks/design.md` how the runners are built. The invocation traps: `npm test` runs two vitest projects, `offline` in node and `interface` in jsdom, and the couplings that cross the language boundary run the agent's half of the shared contracts, so it needs the agent provisioned (`npm run install:agent`). `npm run typecheck` is the only thing that type-checks `src/` — `next.config.ts` sets `ignoreBuildErrors`, so `next build` checks nothing. `validate.py` runs inside the pytest suite and still runs alone for its report. Hydration, layout and the render are seen by no check at all: verify those by running the app with `npm run dev`, which brings up the UI on 3000 and the agent on 8123.

*Conversation checks.* `uv run --env-file ../.env pytest -m scenario` runs the demo scenarios against the live agent; `uv run --env-file ../.env python tests/compare_refs.py <ref>` runs them against two checkouts and reports which assertions moved — the only check that sees a system-prompt or docstring edit at all. Both cost money and are deselected from the default suite. Assertions read tool calls, payloads and state, never prose; that position is measured, not assumed, and the harness's traps (per-call `WORKSPACE_STORE_DIR`, sequential arms) are in `docs/specs/conversation-checks/design.md`. The scenarios it runs are discovery, not a feature — one note each in `docs/discovery/scenarios/`, indexed by `direction.md` under *Examples that make the direction concrete*.

*Model.* The agent runs OpenAI `gpt-5.4-mini` with `parallel_tool_calls` disabled (`agent/main.py`). No spec records why parallel calls are off — treat it as deliberate (the card-click flow assumes one atomic tool call per message) until someone verifies otherwise.

## Writing style

- Write complete sentences and state each claim directly.
- Technical documentation, not marketing copy.
- Banned phrases: "load-bearing", "worth stating plainly", "full stop", "carry the argument", "the trap", "isn't just X — it's Y".
- Do not build to a turn of phrase. State the claim directly.
